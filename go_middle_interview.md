# Go Middle: 500+ вопросов с ответами для подготовки к собеседованию

> Формат: **вопрос → краткий ответ** в стиле «как ответить вслух на собеседовании»: суть, ключевые детали, мини-пример кода там, где он нужен. Ответы сознательно сжатые — это шпаргалка для повторения, а не учебник.

## Как пользоваться

1. Проходи раздел: сначала пытайся ответить вслух, потом сверяйся с ответом.
2. Отмечай вопросы, на которых запнулся (поставь `+` в начале строки вопроса), и возвращайся к ним через день.
3. На собеседовании разворачивай ответ в 30–60 секунд: определение → как устроено внутри → где ловится на практике.

## Раздел 1. Основы языка и типы данных

**1. Из чего состоит минимальная программа на Go?**
Пакет `main` с функцией `main` — точкой входа. Программа собирается из пакетов, пакеты группируются в модули (описываются `go.mod`). Импорты подключаются явно; неиспользуемые импорты и переменные не компилируются.

**2. Какие категории типов есть в Go?**
Примитивные: `bool`, числовые (`int`, `uint`, `int8..int64`, `float32/64`, `complex64/128`, алиасы `byte` и `rune`), `string`. Составные: массивы, срезы, структуры, map, каналы, указатели, функции, интерфейсы.

**3. Что такое нулевое значение (zero value)?**
Значение по умолчанию: `0` для чисел, `false` для bool, `""` для строк, `nil` для указателей/срезов/map/каналов/функций/интерфейсов, нулевая структура для `struct`. В Go нет «неинициализированной» памяти — любой объявленный тип сразу валиден и безопасен для чтения.

**4. Чем отличается `var x = ...` от `x := ...`?**
`:=` — короткое объявление: только внутри функций, тип выводится автоматически. `var` доступен и на уровне пакета, позволяет указать тип явно и объявить без инициализации (получим zero value). Внутри функции `var x int` используют, когда объявление и присваивание разнесены.

**5. Что будет, если объявить переменную или импортировать пакет и не использовать?**
Ошибка компиляции: `declared and not used` / `imported and not used`. Импорт «ради побочных эффектов» (например, драйвер БД) оформляют как `_ "github.com/.../stdlib"`.

**6. Как работают константы и `iota`?**
Константы вычисляются на этапе компиляции; допустимы только базовые типы (числа, строки, bool). `iota` — счётчик внутри блока `const`: начинается с 0 и растёт на каждой строке. Типичное применение — перечисления и битовые маски: `const ( Read = 1 << iota; Write; Exec )`. Пропуск строки — через `_`.

**7. Чем отличается `int` от `int64`?**
`int` платформозависимый: 64 бита на 64-битных системах, 32 — на 32-битных. `int64` — всегда 64. По умолчанию используют `int`; фиксированные размеры нужны для сериализации, сетевых протоколов и битовых операций.

**8. Почему нельзя сравнивать `float64` на точное равенство через `==`?**
Из-за бинарного представления десятичных дробей накапливается погрешность: `0.1 + 0.2 != 0.3`. Сравнивают с допуском (`math.Abs(a-b) < eps`), для денег используют целые копейки (`int64`) или decimal-библиотеки.

**9. Что такое `byte` и `rune`?**
Алиасы: `byte = uint8` (байт), `rune = int32` (Unicode code point). Строка — последовательность байтов в UTF-8; руны нужны, когда работаем с символами, а не с байтами.

**10. Есть ли в Go неявные преобразования типов?**
Нет. Любое преобразование — явное: `int64(i)`, `float64(n)`, `string(b)`. Даже между `int` и `int64` требуется явная конверсия.

**11. Что такое затенение переменных (shadowing) и чем оно опасно?**
Объявление переменной с тем же именем во внутренней области видимости. Классическая ошибка — `err := ...` внутри `if`/цикла затеняет внешний `err`, и ошибка «теряется». Ловится линтерами (shadow-анализаторы, `go vet`).

**12. Как определяется экспортируемость (публичность) идентификаторов?**
Большая первая буква — экспортируемый идентификатор, маленькая — виден только внутри пакета. Отдельных ключевых слов `public/private` нет.

**13. Когда и в каком порядке вызывается `init()`?**
После инициализации пакетных переменных, до `main`. Импортируемые пакеты инициализируются раньше импортирующих; внутри пакета порядок файлов алфавитный, внутри файла — сверху вниз. В одном пакете может быть несколько `init()`.

**14. Зачем нужен пустой идентификатор `_`?**
Пропуск значения при множественном присваивании (`_, ok := m[k]`), игнорирование индекса или значения в `range`, импорт ради побочных эффектов, явное игнорирование ошибки там, где это осознанное решение.

**15. Чем отличается типизированная константа от нетипизированной?**
Нетипизированная (`const x = 5`) имеет «идеальный» тип и неявно подстраивается под контекст: влезет и в `int`, и в `float64`. Типизированная (`const x int64 = 5`) жёстко фиксирует тип.

**16. Какие формы цикла есть в Go?**
Только `for`: классический `for i := 0; i < n; i++`, «как while» (`for cond`), бесконечный (`for {}`) и `for range`. Плюс `for i := range 10` — итерация по числам (Go 1.22).

**17. Что даёт `if` с инициализатором (`if v, ok := m[k]; ok`)?**
Переменные объявляются в области видимости `if`/`else` и не «утекают» наружу. Тот же приём есть в `switch` и в заголовке `for`.

**18. Как работает `switch`?**
Case не требует `break`, «проваливание» в следующий case отключено — `fallthrough` только явно. Несколько значений в одном case: `case 1, 2:`. Есть `switch` без выражения (как цепочка `if`) и type switch: `switch v := x.(type)`.

**19. По чему умеет ходить `for range`?**
Срезы и массивы (индекс + копия элемента), строки (байтовый индекс + руна), map (ключ + значение), каналы (значения до закрытия), целые числа (Go 1.22) и функции-итераторы `func(yield func(K) bool)` (Go 1.23).

**20. Что такое `struct{}` (пустая структура) и где применяется?**
Структура нулевого размера. Применения: множество (`map[string]struct{}`), сигнальный канал (`chan struct{}` — передаётся только факт события), заглушки в реализациях, экономия памяти в больших коллекциях.

## Раздел 2. Срезы

**1. Что такое срез и как он устроен внутри?**
Структура из трёх полей: указатель на underlying-массив, длина `len` и ёмкость `cap`. Заголовок среза занимает 24 байта на 64-битных системах. Срез — это «окно» в массив, а не сами данные.

**2. Чем срез отличается от массива?**
Массив — значение с фиксированной длиной, входящей в тип (`[3]int` и `[4]int` — разные типы), при передаче копируется целиком. Срез — динамический, хранит ссылку на массив, его можно наращивать через `append`.

**3. Чем nil-срез отличается от пустого среза?**
`var s []int` — nil-срез: `len == cap == 0`, `s == nil` — true, underlying-массива нет. `s := []int{}` — не nil, но пустой. Оба безопасны для `len`, `range`, `append`. Различие проявляется в `json.Marshal` (null против `[]`) и при сравнении на nil.

**4. Способы создания среза?**
Литерал `[]int{1, 2, 3}`, `make([]int, 0, n)` (len 0, cap n), `var s []int` (nil-срез), реслайсинг `a[1:3]` от массива или другого среза.

**5. Как работает `append`?**
Возвращает срез (возможно новый). Если `cap` хватает — пишет в существующий массив (и тогда «соседние» срезы видят изменения). Если нет — аллоцирует новый массив, копирует старые данные и пишет туда.

**6. По какой стратегии растёт capacity среза?**
Для маленьких срезов — удвоение; с ростом размера фактор роста плавно снижается примерно до 1.25 (формула менялась между версиями Go; с 1.18 рост плавный). Вывод: не полагаться на точные числа, но понимать амортизированную O(1) сложность `append`.

**7. Главный подводный камень `append` — алиасинг. Что выведет код?**
```go
a := []int{1, 2, 3, 4}
b := a[:2]
b = append(b, 99)
fmt.Println(a)
```
`[1 2 99 4]`: у `b` ещё хватает cap, `append` пишет прямо в массив `a`. Решение — `copy` или полный слайс-выражение (см. вопрос 8).

**8. Что такое полный слайс-выражение `s[low:high:max]`?**
Ограничивает cap результата величиной `max - low`. `b := a[:2:2]` делает так, что следующий `append` обязан выделить новый массив — защита от случайной перезаписи общих данных.

**9. Что делает `copy()`?**
Копирует `min(len(dst), len(src))` элементов, возвращает число скопированных. Приёмник должен быть создан и иметь нужную длину. `copy` работает даже между перекрывающимися срезами.

**10. Как удалить элемент из среза с сохранением порядка?**
`s = append(s[:i], s[i+1:]...)` — сдвиг хвоста влево, O(n). Без сохранения порядка быстрее: `s[i] = s[len(s)-1]; s = s[:len(s)-1]`.

**11. Как вставить элемент в середину среза?**
`s = append(s[:i+1], s[i:]...)` затем `s[i] = x`. Операция O(n).

**12. Почему `b := a` не копия среза?**
Копируется только заголовок: оба среза смотрят в один underlying-массив. Настоящая копия: `b := slices.Clone(a)` или `make` + `copy`.

**13. Срез структур `[]T` или срез указателей `[]*T`?**
`[]T` — компактно и кэш-дружелюбно (одна аллокация при предаллокации), но большие структуры копируются при передаче. `[]*T` — мутации через указатель видны, меньше копий, но n+1 аллокация и разброс по памяти. Для мелких структур чаще `[]T`.

**14. Что происходит при передаче среза в функцию?**
Копируется заголовок (ptr, len, cap). Изменение элементов видно снаружи (общий массив), а `append` с реаллокацией — нет: наружный срез не изменится, поэтому функции, растящие срез, возвращают его.

**15. Как создать двумерный срез?**
```go
m := make([][]int, rows)
for i := range m {
    m[i] = make([]int, cols)
}
```
Литерал `[][]int{{1,2},{3,4}}` тоже валиден.

**16. Как добавить один срез к другому?**
`a = append(a, b...)` — распаковка элементов. Для больших данных это одна реаллокация с копированием.

**17. Как ведёт себя `range` по срезу?**
Возвращает индекс и **копию** элемента: мутация `v` не меняет срез, менять нужно `s[i]`. С Go 1.22 переменные цикла пересоздаются на каждой итерации (до этого — одна переменная, классическая ловушка с замыканиями и горутинами).

**18. Как считаются len и cap у реслайса?**
`s2 := s[1:3]` от среза с len=5, cap=5: `len(s2)=2`, `cap(s2)=4` (cap исходного минус low). Данные общие с исходным срезом.

**19. Что вернут `len` и `cap` у nil-среза? Безопасен ли `append` к нему?**
0 и 0. `append` к nil-срезу корректен и создаёт новый срез — стандартный паттерн `var result []T; result = append(result, x)`.

**20. Почему `sort.Slice` меняет исходный срез?**
Сортировка происходит in-place по underlying-массиву. `sort.Slice` использует рефлексию и замыкание less; `slices.Sort` (Go 1.21) — дженерик и быстрее.

**21. Как взять «хвост» большого среза и не держать в памяти весь массив?**
Скопировать нужную часть в новый срез (`make` + `copy`) либо использовать полный слайс-выражение `s[low:high:high]`. Иначе маленькая «нарезка» удерживает весь большой массив.

**22. Можно ли использовать срез как ключ map?**
Нет — срез не comparable (компилятор запрещает). Массив — можно. Обход: `string([]byte)` для байтовых срезов или сериализация в строку.

**23. Что даёт пакет `slices` (Go 1.21)?**
Дженерик-утилиты: `Contains`, `Index`, `Equal`, `Sort`/`SortFunc`, `Clone`, `Delete`, `Insert`, `Compact`, `BinarySearch`, `Max`/`Min`. Заменяют самописные циклы.

**24. Как удалить дубликаты из среза?**
Отсортированный срез: `slices.Sort` + `slices.Compact`. Неотсортированный с сохранением порядка: вспомогательный `map[T]struct{}` как set.

**25. Зачем предаллокация `make([]T, 0, n)`?**
Убирает серию реаллокаций и копирований при известном (даже приблизительном) размере — меньше CPU и мусора для GC. Стандартная оптимизация в горячем коде.

**26. Как понять, что срез/элемент уехал в heap (escape analysis)?**
`go build -gcflags='-m'`: компилятор печатает `escapes to heap`. Причины: возврат из функции, сохранение в глобальные/долгоживущие структуры, попадание в интерфейс. Локальный срез, не покидающий функцию, может остаться на стеке.

## Раздел 3. Массивы и строки

**1. Что такое массив? Входит ли длина в тип?**
`[3]int` — значение с фиксированным набором элементов; длина — часть типа, поэтому `[3]int` и `[4]int` несовместимы. Массивы сравнимы через `==` (если сравнимы элементы).

**2. Как массив передаётся в функцию?**
По значению — копируется целиком. Поэтому в реальном коде почти всегда используют срезы.

**3. Когда массив уместнее среза?**
Когда размер жёстко фиксирован и данные маленькие: хеши, UUID (`[16]byte`), таблицы констант, матрицы. Массивы дешёвые (без косвенности) и могут жить на стеке.

**4. Как устроена строка внутри?**
Заголовок: указатель на байтовый массив + длина. Строка иммутабельна; «пустая строка» — валидное значение, nil у строк нет.

**5. Что вернёт `len("Привет")` и почему?**
Байты: 12 (6 кириллических букв по 2 байта UTF-8). Количество символов: `utf8.RuneCountInString(s)` или `len([]rune(s))`.

**6. Как работает `range` по строке?**
Итерирует по рунам: индекс — байтовая позиция начала руны, значение — `rune`. Для ASCII индексы идут подряд, для кириллицы/эмодзи — скачут.

**7. Чем дорога конвертация `string <-> []byte`?**
Обе конвертации копируют данные (новая аллокация). Трюки с `unsafe` позволяют избежать копии, но нарушают иммутабельность строки — только при полном понимании последствий.

**8. Как эффективно собирать строку из кусочков в цикле?**
`strings.Builder` (при известном размере — `Grow`): копит байты в одном буфере. Конкатенация `+` в цикле создаёт новую строку на каждом шаге — O(n²).

**9. Почему строки иммутабельны?**
Безопасность: строки-ключи и подстроки могут разделять память без риска изменения. Потокобезопасность: строку можно свободно передавать между горутинами. Изменение — всегда новая строка.

**10. Может ли `s[1:3]` «разрезать» символ кириллицы?**
Да: индексация байтовая, и неаккуратный срез даёт невалидную UTF-8-последовательность (при печати — символ замены `\uFFFD`). Работать с подстроками по байтовым индексам нужно осознанно.

**11. Как правильно получить строку из числа?**
`strconv.Itoa(i)` или `fmt.Sprintf("%d", i)`. Ловушка: `string(65)` — это не «65», а руна U+0041 → `"A"`.

**12. Основные функции пакета `strings`?**
`Contains`, `Index`, `Split`, `Join`, `Replace`/`ReplaceAll`, `TrimSpace`, `Fields` (разбивает по пробелам), `HasPrefix`/`HasSuffix`, `ToUpper`/`ToLower`, `Repeat`, `EqualFold` (сравнение без регистра).

**13. Что умеет пакет `strconv`?**
`Atoi`/`Itoa` для int, `ParseInt`/`FormatInt` с базой и разрядностью, `ParseFloat`/`FormatFloat`, `ParseBool`, `Quote`/`Unquote` для строковых литералов.

**14. Часто используемые глаголы `fmt`?**
`%v` — значение по умолчанию, `%+v` — структура с именами полей, `%#v` — Go-синтаксис, `%T` — тип, `%d` `%s` `%f` `%e`, `%q` — строка в кавычках, `%x` — hex, `%p` — указатель, `%w` — оборачивание ошибки в `fmt.Errorf`.

**15. Как сравниваются строки?**
`==` — байтовое сравнение (сначала длины, затем байты), быстрое. Без учёта регистра (и с Unicode case-folding) — `strings.EqualFold`.

**16. Что такое raw-строки (backticks)?**
`\`...\`` — без escape-последовательностей, могут быть многострочными. Удобны для регулярок, JSON-шаблонов, SQL.

**17. Всегда ли один эмодзи = одна руна?**
Нет. Эмодзи может состоять из нескольких code point (флаги — два regional indicator, модификации тона кожи — additional). Для «человеческих символов» нужны графемные кластеры — библиотека `golang.org/x/text` (segmentation).

**18. Когда нужна конвертация `string -> []rune -> string`?**
Когда обрабатываем символы: переворот строки, посимвольная замена, подсчёт символов. Для чисто байтовых операций (base64, хеширование) руны не нужны.

**19. Как посчитать частоту символов в строке?**
```go
counts := map[rune]int{}
for _, r := range s {
    counts[r]++
}
```

**20. Для чего пакет `bytes`?**
Операции над `[]byte`: `bytes.Buffer`, `Equal`, `Split`, `Contains`, `NewReader`. Часто эффективнее для бинарных данных и в горячих путях.

**21. Делит ли подстрока память с исходной строкой?**
Да, копии нет: подстрока — тот же массив байт с другим заголовком. Это дёшево, но большая строка не освободится, пока жива любая её подстрока (при необходимости — явный `string(sub)` для копии).

**22. Как проверить валидность UTF-8?**
`utf8.ValidString(s)` / `utf8.Valid(b)`. Невалидные последовательности при конвертациях заменяются на U+FFFD.

## Раздел 4. Map

**1. Как устроен map внутри?**
Хеш-таблица из бакетов: в каждом — до 8 пар ключ/значение, байты `tophash` (старший байт хеша для быстрого отсева) и ссылки на overflow-бакеты. Поиск: хеш ключа → индекс бакета → сравнение tophash → полных ключей. При росте (load factor ~6.5) бакеты удваиваются, старые данные эвакуируются **инкрементально** — по мере операций, чтобы не было долгой паузы. С Go 1.24 внутренняя реализация переписана на Swiss Tables, но поведение для пользователя не изменилось.

**2. Какие требования к ключам map?**
Тип ключа должен быть comparable: числа, строки, bool, указатели, каналы, интерфейсы, массивы, структуры из сравнимых полей. Нельзя: срезы, map, функции.

**3. Почему срез нельзя использовать как ключ?**
Равенство срезов не определено (элементы могут меняться со временем). Компилятор запрещает такие ключи.

**4. Что можно делать с nil-map?**
Чтение, `len`, `range`, `delete` — безопасны. Запись — паника `assignment to entry in nil map`. Для записи нужен `make`.

**5. Как проверить наличие ключа?**
```go
v, ok := m[key]
```
`ok == false` — ключа нет, `v` — нулевое значение типа. Одна операция вместо двух.

**6. Что делает `delete(m, k)`?**
Удаляет ключ; отсутствие ключа и nil-map — не ошибка. Ничего не возвращает.

**7. Почему порядок итерации по map случайный?**
Рантайм специально рандомизирует стартовую точку обхода, чтобы код не зависел от порядка (реализация и порядок растут между версиями). Детерминированный вывод — собрать ключи, отсортировать, итерировать по срезу.

**8. Является ли map потокобезопасным?**
Нет. Параллельные запись/чтение-запись дают **fatal error** `concurrent map writes` — это не паника, recover не спасает, процесс падает. Race detector находит такие места заранее.

**9. Как защитить map в конкурентной среде?**
`sync.RWMutex` вокруг map, `sync.Map` (для специфичных нагрузок) или передача владения через одну горутину-владельца.

**10. Когда использовать `sync.Map`?**
Read-heavy нагрузка и стабильный набор ключей: кэши, реестры, разовые записи при чтениях. Внутри — два слоя: lock-free `read` + mutex-защищённый `dirty`. Для частых записей и связанных ключей `mutex + map` быстрее и понятнее.

**11. Как сделать множество (set) на Go?**
`map[T]struct{}`: нулевой размер значения. Проверка: `_, ok := set[x]`.

**12. Можно ли использовать структуру как ключ?**
Да, если все поля comparable. Опасность: мутабельные поля. Изменил поле — ключ «потерялся» в map. Лучше неизменяемые ключи или хранить указатель в значении.

**13. Зачем указывать ёмкость при создании?**
`make(map[string]int, n)` — предаллокация под n элементов, меньше рехешей. Полезно при известном объёме загрузки.

**14. Как скопировать map?**
Только вручную: создать новую, обойти исходную в `range`, вставить элементы. Встроенного copy нет.

**15. Как очистить map?**
`clear(m)` (Go 1.21+) — очищает без реаллокации. Альтернатива — присвоить новую map: старая уйдёт в GC целиком.

**16. Возвращается ли память после `delete`?**
Практически нет: бакеты остаются в таблице, map почти не уменьшается. Если удалили много и map долгоживущая — пересоздать её (или `clear` + перезаливка, или новая map).

**17. Почему нельзя взять адрес элемента map (`&m[k]`)?**
При рехеше элементы переезжают между бакетами — адрес стал бы висячим. Из-за этого же нельзя менять поле структуры по месту: `m[k].Field = x` — ошибка компиляции.

**18. Как изменить поле структуры-значения в map?**
```go
v := m[k]
v.Field = x
m[k] = v
```
Или хранить указатели: `map[string]*T` — тогда `m[k].Field = x` работает.

**19. Что будет, если модифицировать map во время `range`?**
Это разрешено: удалённые элементы не будут посещены, вставленные во время итерации — могут быть или не быть (недетерминированно). Удалять «на ходу» — безопасный приём.

**20. Какие типы ключей поддерживает encoding/json?**
Ключи должны быть строками, целыми числами или реализовывать `encoding.TextMarshaler`. Для любых других типов маршаля выдаст ошибку.

**21. Как вывести map в отсортированном порядке?**
```go
keys := make([]string, 0, len(m))
for k := range m { keys = append(keys, k) }
sort.Strings(keys)
for _, k := range keys { fmt.Println(k, m[k]) }
```

**22. Какая хеш-функция используется для ключей?**
Встроенная рантайм-хеш-функция (для строк и байтов — memhash, на части платформ с AES-инструкциями), не криптографическая, с рандомизацией на процесс для защиты от коллизионных атак. Свою хеш-функцию подключить нельзя.

## Раздел 5. Структуры и методы

**1. Как объявить и создать структуру?**
```go
type Point struct{ X, Y int }
p1 := Point{1, 2}          // позиционно
p2 := Point{X: 1}          // именованно, Y = 0
p3 := new(Point)           // *Point с нулевыми полями
var p4 Point               // нулевая структура
```

**2. Можно ли сравнивать структуры через `==`?**
Да, если все поля comparable — сравнение идёт по полям. Структура со срезом, map или функцией в полях не сравнима (компилятор запретит).

**3. Что такое встраивание (embedding)?**
Поле без имени: `type Service struct { Logger }`. Методы и поля встроенного типа «поднимаются» на внешний тип: `s.Info()` вместо `s.Logger.Info()`. Это **композиция, не наследование**: нет полиморфизма подтипов, встроенный тип ничего не знает о внешнем.

**4. Как разрешаются конфликты имён при встраивании?**
Одинаковые имена на одном уровне — ошибка при обращении. На разных уровнях побеждает более «близкий» к внешнему типу метод.

**5. Value receiver против pointer receiver — как выбирать?**
`func (s Service) Do()` работает с копией; `func (s *Service) Do()` — с оригиналом. Pointer receiver: метод мутирует состояние, структура большая, нужен единый набор методов. Value receiver: маленькие иммутабельные типы (векторы, ключи). Смешивать в одном типе не стоит.

**6. Что такое method set и как он влияет на интерфейсы?**
У типа `T` в наборе — методы с value receiver. У `*T` — и value, и pointer receiver. Поэтому `*T` реализует больше интерфейсов, чем `T`. Метод с pointer receiver нельзя вызвать «через» значение, у которого нельзя взять адрес (например, элемент map или значение в интерфейсе).

**7. Почему нельзя вызвать pointer-receiver метод у элемента map?**
`m[k]` не адресуем (элементы переезжают при рехеше). Решение: `map[string]*T` или чтение-изменение-запись значения.

**8. `new(T)` против `&T{}`?**
Оба возвращают `*T` с нулевыми полями. `&T{X: 1}` — сразу с инициализацией. `new` удобен для «готового указателя на нулевое значение», используется реже.

**9. Что происходит при копировании структуры с указателями?**
Поверхностное копирование: копируются сами указатели, оба объекта ссылаются на одни данные. Глубокая копия — вручную (по полям) или через сериализацию.

**10. Зачем нужна пустая структура в полях и каналах?**
`struct{}` занимает 0 байт. Примеры: `map[string]struct{}` (set), `chan struct{}` (сигнал), реализация интерфейса «пустышкой».

**11. Что такое теги структур и как их читают?**
Строковые метаданные после поля: `Name string \`json:"name,omitempty"\``. Читаются через рефлексию (`reflect.Type.Field.Tag`) — так работают encoding/json, валидаторы, ORM.

**12. Что такое анонимная структура?**
Тип без имени, объявленный на месте: `var cfg struct { Port int; Host string }`. Удобно для одноразового парсинга конфига или тестовых данных.

**13. Можно ли вызвать метод у nil-указателя?**
Да, если метод не разыменовывает receiver: `func (u *User) Valid() bool { return u != nil }` — валидный вызов `var u *User; u.Valid()`. Разыменование nil — паника.

**14. Как добавить метод к типу из другого пакета?**
Никак: receiver должен быть из текущего пакета. Обход — обёртка: `type MyTime time.Time` + свои методы, или функции-хелперы.

**15. Что будет при обращении к полям nil-встроенного указателя?**
`type A struct { *B }`: если `B` не присвоен, обращение `a.FieldB` — паника (nil pointer dereference).

**16. Как порядок полей влияет на размер структуры?**
Компилятор выравнивает поля по границам слов: `[bool, int64, bool]` может занимать 24 байта против 16 у `[int64, bool, bool]`. Проверка — `unsafe.Sizeof`. «Горячие» поля группируют в начале.

**17. Как красиво распечатать структуру?**
`%v` → `{1 2}`, `%+v` → `{X:1 Y:2}`, `%#v` → `main.Point{X:1, Y:2}`. В логах — `%+v` или структурное логирование.

**18. Влияют ли неэкспортируемые поля на сериализацию?**
Строчные (незкспортируемые) поля `encoding/json` игнорирует, теги на них не помогут. Публичный API структуры — только с большой буквы.

**19. Как объявить самоссылающуюся структуру?**
`type Node struct { Val int; Next *Node }` — через указатель, иначе размер типа был бы бесконечным.

**20. Каков идиоматичный «конструктор» в Go?**
Функция `NewT(...)` / `NewT(...) (T, error)`, инициализирующая все поля в валидное состояние. После конструктора объект должен быть готов к использованию без дополнительных сеттеров.

**21. Когда структуру передавать по значению, а когда по указателю?**
Маленькие структуры (несколько слов) — по значению: дёшево и без нагрузки на GC. Большие или мутируемые — по указателю. Согласованность внутри типа важнее микронанов.

**22. Сработает ли вызов value-receiver метода через указатель?**
Да, синтаксический сахар: `p.Do()` превращается в `(*p).Do()`, когда переменная адресуемая.

**23. Можно ли конвертировать структуры с одинаковыми полями, но разными тегами?**
Да: с Go 1.8 структуры, идентичные кроме тегов, взаимно конвертируемы. Это основа приёмов с DTO-типами.

**24. Как хранить коллекцию структур с мутациями?**
`[]*T` или `map[K]*T` — мутации по указателю видны всем держателям. С `[]T` мутации элемента требуют записи обратно `s[i] = v`.

## Раздел 6. Указатели

**1. Что делают операторы `&` и `*`?**
`&x` — адрес переменной (тип `*T`), `*p` — разыменование (значение по адресу). Указатель нулевой — `nil`.

**2. Что произойдёт при разыменовании nil-указателя?**
Паника `runtime error: invalid memory address or nil pointer dereference`. Защита — проверка `if p != nil` или паттерн «nil-safe методы».

**3. Есть ли арифметика указателей?**
В безопасном Go нет. Только через `unsafe.Pointer` + `uintptr` — для системного кода, в обычных проектах не нужен.

**4. Чему нельзя взять адрес?**
Константам, литералам, элементам map, результатам функций, значениям, хранящимся в интерфейсе. Переменным, полям структур, элементам массивов и срезов — можно.

**5. Где живёт локальная переменная, на которую взяли указатель и вернули из функции?**
В heap — escape analysis переносит её туда автоматически. Код остаётся безопасным, GC следит за жизнью объекта. Проверить решение компилятора: `go build -gcflags='-m'`.

**6. Указатель или значение в параметрах функции?**
Указатель: мутации видны вызывающему, нет копии большой структуры; ценой — нагрузка на GC и косвенный доступ. Значение: изоляция от изменений, кэш-дружелюбность. Мелкие структуры дешевле передавать по значению.

**7. Когда нужен указатель на указатель `**T`?**
Редко: когда функция должна заменить сам указатель (рефлексия, десериализация сложных структур, some API-пэти). В обычном коде — запах.

**8. Как сравниваются указатели?**
`==` сравнивает адреса. Два указателя на один объект равны; сравнение с `nil` — стандартный паттерн проверки.

**9. Нужен ли указатель на интерфейс (`*MyInterface`)?**
Практически никогда: интерфейс и так «ссылочный» (пара тип+данные). `*SomeInterface` в сигнатуре — красный флаг.

**10. Что такое `unsafe.Pointer` и когда он нужен?**
Тип для обхода системы типов: конверсии между несовместимыми типами, арифметика через `uintptr`, FFI/CGO, низкоуровневые оптимизации. Ломает гарантии компилятора — только в коде, где без этого никак.

**11. Чем опасен указатель на элемент среза/массива?**
При росте среза (реаллокация) или перестановках указатель продолжает смотреть на старый массив. Держать такие указатели долго — источник багов.

**12. Что происходит с данными, когда указатель обнуляется (`p = nil`)?**
Сам объект не исчезает мгновенно: он станет мусором, когда не останется ссылок, и его соберёт GC. «Освобождение» в Go — только через отсутствие ссылок.

## Раздел 7. Интерфейсы

**1. Что такое интерфейс в Go?**
Набор методов. Тип реализует интерфейс **неявно** — достаточно реализовать все методы с нужными сигнатурами (структурная типизация). Ключевого слова «implements» нет.

**2. Как интерфейс устроен в рантайме?**
Пара (динамический тип, динамическое значение): itab — метаданные типа + таблица методов — и указатель на данные. Интерфейс равен nil, только если **оба** поля нулевые.

**3. Классическая ловушка: интерфейс с nil-указателем. Объясните.**
```go
func f() error {
    var e *MyErr // nil
    return e     // интерфейс: (тип *MyErr, значение nil)
}
err := f()
fmt.Println(err == nil) // false!
```
Интерфейс не nil, потому что тип записан. Правило: возвращать `nil` как `error` явно, не возвращать конкретные nil-указатели в интерфейсных типах.

**4. Что такое `any`?**
Алиас `interface{}` (Go 1.18). Хранит любое значение. В современном коде пишут `any`.

**5. Как работает type assertion?**
`v := x.(T)` — паника, если динамический тип другой. `v, ok := x.(T)` — безопасная форма. Ассершн работает только по типу, а не «по наличию методов».

**6. Что такое type switch?**
```go
switch v := x.(type) {
case int:    ...
case string: ...
default:     ...
}
```
Разбор динамического типа по веткам; в `v` попадает значение нужного типа.

**7. Что хранится в интерфейсе — копия?**
Да, при присваивании значение копируется (боксинг). Мутация исходной переменной не видна через интерфейс. Если в интерфейсе указатель — копируется указатель, мутации по нему видны.

**8. Почему `T` не реализует интерфейс, а `*T` реализует?**
Если у `T` есть методы с pointer receiver, их набор принадлежит только `*T`. Паттерн `var _ I = (*T)(nil)` — компиляционная проверка без создания объекта.

**9. Как объединять интерфейсы?**
Встраиванием: `type ReadWriteCloser interface { io.Reader; io.Writer; io.Closer }`. Получаем композицию контрактов.

**10. Назовите важные интерфейсы стандартной библиотеки.**
`io.Reader`/`io.Writer`, `error`, `fmt.Stringer` (`String()`), `sort.Interface`, `json.Marshaler`/`json.Unmarshaler`, `context.Context`, `http.Handler`, `encoding.TextMarshaler`.

**11. Где объявлять интерфейс — у поставщика или потребителя?**
У потребителя: сервис объявляет интерфейс из тех методов, что ему нужны; реализация подключается снаружи. Маленькие интерфейсы проще мокать и реализовывать.

**12. Сколько стоит вызов метода через интерфейс?**
Динамическая диспетчеризация: косвенный вызов через таблицу методов (хуже предсказывается CPU), плюс возможный боксинг в heap. В горячих циклах — конкретные типы или дженерики.

**13. Чем опасно сравнение интерфейсов через `==`?**
Интерфейсы равны, если равны типы и значения. Но если динамический тип несравним (срез, map, функция) — паника `comparing uncomparable type`. Проверять через type switch, если риск есть.

**14. Что делает `var _ I = (*T)(nil)`?**
Компилятор проверяет, что `*T` реализует `I`, не создавая экземпляр. Идиома фиксации контракта рядом с типом.

**15. Как обычная функция становится `http.Handler`?**
`http.HandlerFunc` — именованный тип функции с методом `ServeHTTP`. Любая `func(w,r)` приводится к `http.Handler`. Это паттерн «функциональный адаптер».

**16. Зачем нужен интерфейс с неэкспортируемым методом?**
Реализовать его могут только типы внутри того же пакета — способ запретить внешние реализации (например, у `context.Context` метод `Deadline() (deadline time.Time, ok bool)` плюс скрытые детали; типичный пример — идиомы с приватными методами в пакетах stdlib).

**17. Почему маленькие интерфейсы — это хорошо?**
1–2 метода: легко реализовать для тестов, легко удовлетворить множеству типов, шире применимость. `io.Reader` — эталон: сотни совместимых типов.

**18. Интерфейсы против дженериков — как выбирать?**
Интерфейс: разнотипные значения в одной коллекции, динамическая диспетчеризация, DI. Дженерик: один и тот же алгоритм для разных типов без боксинга и вызовов через таблицу.

**19. Когда `any` в сигнатуре — антипаттерн?**
Когда тип реально известен: `any` убирает контракт и проверки на компиляции. Уместен — для сериализации, декораторов, «карго»-хранилищ (`context.Value`).

**20. Что происходит при вызове метода у nil-интерфейса?**
Паника (nil interface value). Проверять `err != nil` до вызова методов.

**21. «Принимай интерфейсы, возвращай структуры» — почему?**
Параметр-интерфейс даёт гибкость вызывающему; возврат конкретного типа сохраняет информацию и не заставляет потребителя ассертить. Правило не абсолютное (иногда возвращают интерфейс для скрытия деталей), но базовое.

**22. Как интерфейсы помогают в тестировании?**
Зависимость объявляется интерфейсом, тест подставляет фейк с нужными методами — без реальной БД/сети. Мокается только то, что реально используется сервисом.

**23. Может ли интерфейс реализовать интерфейс?**
Любой интерфейс автоматически удовлетворяет интерфейсу с подмножеством его методов: `io.ReadWriteCloser` реализует `io.Reader`.

**24. Что напишет компилятор, если тип не реализует интерфейс?**
`T does not implement I (method X has pointer receiver)` — точный указатель, чего не хватает. По этой причине проверку `var _ I = T{}` держат рядом с типом.

**25. Сколько «стоит» присваивание значения в интерфейс?**
Копия значения (если не указатель) + потенциальная аллокация в heap (боксинг). Маленькие скаляры дёшевы; большие структуры в горячем коде — передавать указателем.

**26. Как безопасно проверить тип в горячем коде?**
Type switch быстрее серии `.(T)` (одна диспетчеризация). Для сложных сценариев — дженерики, убирающие ассерты вообще.

## Раздел 8. Ошибки

**1. Что такое `error` в Go?**
Встроенный интерфейс: `type error interface { Error() string }`. Ошибка — обычное значение, возвращаемое последним: `v, err := f()`. Обработка — через `if err != nil`.

**2. `errors.New` против `fmt.Errorf`?**
`errors.New("msg")` — статичный текст без форматирования. `fmt.Errorf("user %d not found", id)` — форматирование. С `%w` — оборачивание нижестоящей ошибки.

**3. Как создать свой тип ошибки?**
```go
type ValidationError struct { Field string; Msg string }
func (e *ValidationError) Error() string { return e.Field + ": " + e.Msg }
```
Преимущество — ошибки несут структуру, которую можно достать через `errors.As`.

**4. Что такое оборачивание ошибок (Go 1.13+)?**
`fmt.Errorf("load config: %w", err)` — новая ошибка хранит цепочку через `Unwrap()`. По цепочке ходят `errors.Is`, `errors.As`, `errors.Unwrap`.

**5. Чем `errors.Is` лучше `==`?**
`==` сравнивает только саму ошибку; `errors.Is` проходит всю цепочку unwrapping и учитывает метод `Is(error) bool` у кастомных ошибок. Всегда предпочитайте `Is`.

**6. Как достать конкретный тип ошибки из цепочки?**
```go
var pathErr *fs.PathError
if errors.As(err, &pathErr) { fmt.Println(pathErr.Path) }
```
`errors.As` ищет первый подходящий тип по цепочке.

**7. Что делает `errors.Join`?**
Объединяет несколько ошибок в одну (Go 1.20): реализует `Unwrap() []error`, поэтому `errors.Is/As` работают по всем частям. Применяют, когда нужно собрать ошибки всех шагов, а не падать на первой.

**8. Что такое sentinel-ошибки?**
Пакетные значения: `var ErrNotFound = errors.New("not found")`. Проверка — `errors.Is`. Плюсы: простота. Минусы: сравнение по «строковой идентичности», нет данных. Для информации — типизированные ошибки.

**9. Как сохранять контекст ошибки по слоям?**
Оборачивать на каждом уровне: `fmt.Errorf("read file %s: %w", path, err)`. Наверху лог с полным «путём» причин, без потери исходной ошибки.

**10. Почему «залогировать и вернуть» — антипаттерн?**
Ошибка залогируется дважды (здесь и наверху) или контекст дублируется. Правило: внутри — только оборачивать; логировать один раз на границе (handler/entrypoint).

**11. Когда ошибка, а когда паника?**
Ожидаемые ситуации (валидация, IO, сеть, отсутствие записи) — ошибка. Нарушение инварианта, баг программиста (nil там, где не может быть) — паника допустима. Библиотеки почти никогда не паникуют наружу.

**12. Как проверить «файл не существует»?**
`errors.Is(err, fs.ErrNotExist)` — работает и для `*fs.PathError`, и для обёрток.

**13. Как выглядит типичная системная ошибка?**
`*fs.PathError{Op: "open", Path: "...", Err: ...}`, `*net.OpError`, `*os.SyscallError` — операция + объект + причина. Достаются через `errors.As`.

**14. Как пометить ошибку как «повторяемую» (retryable)?**
Поле в структуре ошибки (`Retryable bool`) или метод-интерфейс (`Temporary() bool`). Ретрай-механизм проверяет через `errors.As`/интерфейс-каст.

**15. Как собирать ошибки из параллельных горутин?**
`golang.org/x/sync/errgroup`: `g.Go(func() error {...})`, `g.Wait()` возвращает первую ошибку. Если нужны все — собирать в срез и `errors.Join`.

**16. Зачем `errgroup.WithContext`?**
`g, ctx := errgroup.WithContext(ctx)` — контекст отменяется при первой ошибке любой задачи: остальные работы останавливаются, не дожидаясь.

**17. Как различать `context.Canceled` и `context.DeadlineExceeded`?**
`errors.Is(err, context.Canceled)` / `errors.Is(err, context.DeadlineExceeded)`. Отменённое клиентом ретраить не нужно, дедлайн — возможно, но с новыми ресурсами.

**18. Как ошибки превращаются в ответы API?**
Маппинг на границе транспорта: доменные ошибки → HTTP-статусы (404/409/422) или gRPC-коды. Наружу — без внутренних деталей и стеков; для корреляции — request-id в логах.

**19. Нужны ли стек-трейсы в ошибках?**
Стандартный `error` стека не содержит. Обычно достаточно «цепочки причин» в сообщении. Трейсы — опционально через обёртки в точке входа, а не в каждом вызове.

**20. Как тестировать ошибки?**
Table-driven: поле `wantErr error` + `errors.Is` (или `assert.EqualError` для точного текста). Проверять и тип (через `As`), и «политику» (retryable).

**21. Как изолировать детали БД от домена?**
Репозиторий транслирует ошибки драйвера в доменные: `pgconn.PgError` с кодом 23505 → `ErrDuplicateUser`. Слои выше не знают про SQL.

**22. Что делать с `sql.ErrNoRows`?**
`errors.Is(err, sql.ErrNoRows)` — `QueryRow` ничего не нашёл. Часто транслируется в доменную `ErrNotFound` на уровне репозитория.

## Раздел 9. Паники, recover и defer

**1. Что такое panic?**
Аварийная остановка нормального потока выполнения: раскрутка стека с выполнением всех defer'ов. Не перехваченная паника роняет процесс с трейсом всех горутин.

**2. Как работает `recover()`?**
Останавливает раскрутку и возвращает значение паники, но **только** если вызван напрямую в отложенной функции той же горутины. Вне defer — всегда `nil`.

**3. Что будет при панике в горутине?**
Процесс умрёт целиком. `recover` из другой горутины не помогает — каждый «внешний» вход в горутину оборачивают в defer/recover, если нельзя допустить падение.

**4. Когда паника уместна?**
Ошибки инициализации (must-хелперы: `MustCompile`, конфиг без которого не стартуем), нарушения инвариантов («не может случиться»), тесты. В библиотечном коде — почти никогда.

**5. Что происходит с `panic(nil)`?**
С Go 1.21 он превращается в `*runtime.PanicNilError` (recover вернёт эту ошибку), чтобы не терять факт паники. Старое поведение — через `GODEBUG=panicnil`.

**6. Типичные runtime-паники?**
Index out of range, nil pointer dereference, запись в nil map, неудачный type assertion, `concurrent map writes`, send on closed channel, close of closed channel.

**7. В каком порядке выполняются defer'ы?**
LIFO: последний зарегистрированный — первым выполняется.

**8. Когда вычисляются аргументы отложенной функции?**
В момент регистрации `defer`. `defer fmt.Println(i)` запомнит текущее `i`. Замыкание `defer func() { fmt.Println(i) }()` увидит финальное значение.

**9. Чем отличается defer с замыканием от defer с аргументом?**
Аргумент копируется сразу; замыкание захватывает переменную по ссылке и читает её при выполнении. Это ключ к пониманию «странного» порядка вывода.

**10. Как defer взаимодействует с named return values?**
Порядок: `return x` присваивает результат → выполняются defer'ы → выход. Отложенная функция может изменить именованный результат:
```go
func f() (x int) {
    defer func() { x++ }()
    return 1 // вернётся 2
}
```

**11. Чем плох defer внутри цикла?**
Defer'ы копятся до конца функции — ресурсы (файлы, соединения) не освободятся вовремя. Оборачивать итерацию в функцию: `for ... { func() { f, _ := os.Open(...); defer f.Close(); ... }() }`.

**12. Сколько стоит defer?**
С Go 1.14 «open-coded defers» — почти бесплатно в типичных случаях. Но defer в цикле — всё равно проблема семантики, не производительности.

**13. Кто перехватывает паники в HTTP-хендлерах?**
`net/http` сам оборачивает обработку соединения: паника в хендлере не роняет сервер — соединение закрывается, ошибка в лог. Но собственные горутины и middleware — ваша ответственность.

**14. Как сделать recover-middleware?**
```go
func Recover(h http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if rec := recover(); rec != nil {
                log.Error("panic", "err", rec)
                http.Error(w, "internal error", http.StatusInternalServerError)
            }
        }()
        h.ServeHTTP(w, r)
    })
}
```

**15. В какой момент выполняются defer относительно `return` вызывающей функции?**
После вычисления результата `return`, до передачи управления вызывающему.

**16. Выполняются ли defer при `os.Exit`?**
Нет. `os.Exit` (и `log.Fatal`) завершает процесс немедленно — defer'ы, flush буферов и горутины игнорируются.

**17. Что такое `runtime.Goexit()`?**
Завершает текущую горутину без паники, defer'ы выполняются. Используется внутри `testing` (`t.FailNow`).

**18. Как защититься от двойного закрытия канала в панических сценариях?**
Владение каналом: закрывает только создатель-отправитель, ровно один раз, через `sync.Once` при нескольких отправителях. Обёртки «safe close» — костыль; правильная архитектура лучше.

## Раздел 10. Горутины

**1. Что такое горутина?**
Легковесный поток в рантайме Go, планируемый на потоки ОС в модели M:N. Стартовый стек ~2 КБ (растёт динамически до 1 ГБ), создание и переключение — микросекунды. В отличие от потока ОС, горутина управляется планировщиком Go, а не ядром.

**2. Как запускается горутина и что важно помнить?**
`go f()` / `go func(){...}()`. Выполнение асинхронное: без синхронизации (каналы, WaitGroup) `main` может завершиться раньше горутин, и они не выполнятся.

**3. Как остановить горутину?**
Прямого kill нет. Паттерны: канал `done` + `close`, `context` отмены, закрытие канала-источника. Горутина должна сама проверять сигнал и завершаться.

**4. Что такое утечка горутины и как её найти?**
Горутина навсегда заблокирована (читает канал, который никто не закроет; ждёт таймер; держит mutex). Приводит к росту памяти и мусору планировщика. Поиск: профиль goroutine в pprof (снимки растут), `goleak` в тестах, метрика `runtime.NumGoroutine`.

**5. Что происходит с горутинами при завершении `main`?**
Процесс завершается, все горутины убиваются мгновенно, defer'ы не выполняются, буферы не сбрасываются.

**6. Сколько горутин можно создать?**
Сотни тысяч–миллионы: стек 2 КБ, дешёвое переключение. Ограничение на практике — память и логика приложения, а не рантайм.

**7. Что такое GOMAXPROCS?**
Число P (логических процессоров) планировщика; по умолчанию — число CPU. В контейнерах с CPU-лимитами с Go 1.25 учитывается автоматически (раньше — `uber-go/automaxprocs`). Менять вручную нужно редко.

**8. Ловушка с переменной цикла в горутинах?**
До Go 1.22:
```go
for _, v := range xs {
    go func() { use(v) }() // все видят ОДНУ v → мусор
}
```
Фикс — `go func(v T){ use(v) }(v)`. С Go 1.22 переменная цикла пересоздаётся на итерации, баг исчез, но вопрос на собесах жив.

**9. Чем передавать данные между горутинами?**
Каналы (передача владения), мьютексы (защита общего состояния), atomic (простые счётчики/флаги). Принцип: «не гоняйтесь за памятью — передавайте владение».

**10. Канонический паттерн WaitGroup?**
```go
var wg sync.WaitGroup
for i := 0; i < n; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        work()
    }()
}
wg.Wait()
```
`Add` — до `go`, `Done` — через defer. С Go 1.25 есть `wg.Go(func(){...})`, делающий это автоматически.

**11. Что даёт `errgroup`?**
`golang.org/x/sync/errgroup`: как WaitGroup, но `Wait()` возвращает первую ошибку; `WithContext` отменяет контекст при ошибке; `SetLimit(n)` ограничивает параллелизм. Стандартный инструмент для «сделать N задач с лимитом и отменой».

**12. Зачем передавать значение параметром горутине, а не захватывать?**
Параметр — своя копия на горутину: нет гонки и зависимости от внешних изменений. Захват — общая переменная (опасно, особенно до Go 1.22).

**13. Как выглядит «вечный» воркер?**
```go
for {
    select {
    case <-ctx.Done():
        return
    case job := <-jobs:
        process(job)
    }
}
```

**14. Как посмотреть число живых горутин?**
`runtime.NumGoroutine()` — полезная метрика для мониторинга утечек.

**15. Что делает горутина при блокирующем syscall?**
Планировщик отделяет P от занятого M (поток уходит в syscall) и отдаёт P другому M — процессор продолжает выполнять другие горутины.

**16. Сколько стоит создание горутины?**
Пара микросекунд и ~2–8 КБ памяти. Канал — порядка сотни байт. Узкие места обычно в архитектуре, а не в цене создания.

**17. Как не уронить сервис паникой в горутине?**
Обёртка:
```go
func SafeGo(f func()) {
    go func() {
        defer func() { _ = recover() /* + лог */ }()
        f()
    }()
}
```
Все самостоятельные `go f()` в сервисе — через такую обёртку.

**18. Как ограничить число одновременно работающих горутин?**
Семафор из буферизированного канала (`chan struct{}`, cap = N), `errgroup.SetLimit(n)` или пул воркеров + очередь. Неограниченный `go` на каждый запрос — путь к OOM.

## Раздел 11. Каналы

**1. Что такое канал?**
Типизированный конвейер для коммуникации горутин: отправка/приём значений + синхронизация. `make(chan T)` — небуферизированный, `make(chan T, n)` — буферизированный.

**2. Блокирующая семантика операций?**
Небуферизированный: отправка ждёт приёмника, приём ждёт отправителя (rendezvous). Буферизированный: блокируется при полном буфере (отправка) или пустом (приём).

**3. Что такое направленные каналы?**
`chan<- T` — только отправка, `<-chan T` — только приём. Двусторонний канал автоматически сужается при передаче. Направления фиксируют контракт в сигнатурах функций.

**4. Что происходит с nil-каналом?**
`var ch chan T` — nil. Любая операция (send/receive) блокируется навсегда. В select кейс с nil-каналом никогда не готов — используют для отключения веток.

**5. Что вернёт чтение из закрытого канала?**
Немедленно: нулевое значение + `ok = false` (`v, ok := <-ch`). Если в буфере остались данные — сначала они.

**6. Что будет при отправке в закрытый канал?**
Паника `send on closed channel`.

**7. Кто закрывает канал?**
Отправитель (или координатор отправителей — через `sync.Once`, если их несколько). Приёмник не закрывает. Повторное `close` — паника. `close(nil)` — паника.

**8. Зачем вообще закрывать канал?**
Сигнал «данных больше не будет»: завершает `range` по каналу, выводит получателей из блокировки (broadcast — все ждущие получат нулевое значение).

**9. Как работает `range` по каналу?**
`for v := range ch` — читает значения, пока канал не закрыт; после закрытия цикл завершается.

**10. Как канал устроен внутри?**
Структура `hchan`: кольцевой буфер, мьютекс рантайма, очереди ждущих отправителей и получателей (`sudog`). Небуферизированный канал передаёт значение напрямую из горутины в горутину, минуя буфер.

**11. Что показывают `len(ch)` и `cap(ch)`?**
Число элементов в буфере и ёмкость. Только для диагностики/метрик — строить логику на `len` ненадёжно (состояние меняется конкурентно).

**12. Мьютекс или канал — как выбирать?**
Защита общего состояния (кэш, счётчик, структура) — мьютекс/atomic. Передача потока данных и владения, оркестрация — каналы. «Не общайтесь через общую память — делите память, передавая её».

**13. Что такое дедлок «all goroutines are asleep»?**
Runtime видит, что все горутины заблокированы на каналах/локах — fatal error. Локальный дедлок части горутин рантайм не ловит — только диагностика (pprof goroutine).

**14. Зачем канал `chan struct{}`?**
Сигнальный: важен факт события, а не значение. `close(done)` — разбудить всех ждущих без данных.

**15. Как сделать операцию с таймаутом?**
```go
select {
case v := <-ch: ...
case <-time.After(d): // таймаут
}
```
В цикле `time.After` аллоцирует таймер на каждой итерации — лучше `time.NewTimer` + `Reset`.

**16. Паттерн done-канала / отмена через ctx?**
```go
select {
case res := <-resultCh: use(res)
case <-ctx.Done(): return ctx.Err()
}
```
Стандарт для «результат или отмена».

**17. Как слить несколько каналов в один (fan-in)?**
Горутина на каждый источник пишет в общий выход; `WaitGroup` ждёт все, затем `close(out)`. С ctx — select с отменой в каждой ветке.

**18. Что такое fan-out?**
Несколько воркеров читают один канал: готовые получают следующую задачу — естественная балансировка нагрузки.

**19. Как остановить потребителя, читающего в range?**
Закрыть канал со стороны источника, либо перейти на `select` с `ctx.Done()`.

**20. Как ведёт себя канал при передаче в функцию?**
Канал — ссылочный тип: копия заголовка указывает на тот же канал. В сигнатурах сужать направление: `func consumer(ch <-chan T)`.

**21. Как выбирать ёмкость канала?**
0 — строгая синхронизация «рука в руку». N — сглаживание пиков при известном объёме. Большой буфер — не решение проблемы перегрузки (backpressure откладывается, а не исчезает).

**22. Когда select, а когда range?**
`range` — единственный источник данных. `select` — несколько источников, таймауты, отмена.

**23. Паттерн «генератор»?**
```go
func gen(ctx context.Context, xs []T) <-chan T {
    out := make(chan T)
    go func() {
        defer close(out)
        for _, x := range xs {
            select {
            case out <- x:
            case <-ctx.Done():
                return
            }
        }
    }()
    return out
}
```

**24. Как закрытие канала работает как broadcast?**
`close(quit)`: все горутины, стоящие на `<-quit`, одновременно получат нулевое значение и продолжат. Один сигнал — много получателей.

**25. Почему нельзя закрывать канал на приёмной стороне?**
Отправитель, который ещё не закончил, получит панику. Владение: тот, кто пишет, тот и закрывает; если закрытие нужно снаружи — передайте dedicated-канал управления.

**26. Сводка паникоопасных операций с каналами?**
Send в закрытый канал, `close` уже закрытого, `close(nil)` — паники. Send/receive на nil-канале — вечная блокировка (не паника).

## Раздел 12. Select

**1. Что делает `select`?**
Ожидает готовности одной из канальных операций; выполняет готовый case. Блокирует, если ни один не готов и нет `default`.

**2. Что будет, если готовы несколько case?**
Выбор псевдослучайный и равновероятный — защита от голодания отдельных веток.

**3. Что даёт `default`?**
Немедленный «промах»: select не блокируется. Основа non-blocking send/receive (проверить очередь и уйти).

**4. Что делает пустой `select {}`?**
Блокирует горутину навсегда.

**5. Как «отключить» ветку select динамически?**
Установить канал в nil: кейс с nil-каналом никогда не готов. Классика: после закрытия канала-источника `ch = nil`, чтобы не спамить нулевыми значениями.

**6. Select без default и без готовых каналов?**
Блокируется до готовности любого кейса.

**7. Select на закрытом канале?**
Чтение всегда «готово» (нулевое значение, ok=false). Если в select несколько источников — закрытый может «перехватывать» выбор. Решение: проверять ok и обнулять канал.

**8. Канонический воркер на select?**
```go
for {
    select {
    case <-ctx.Done(): return
    case job, ok := <-jobs:
        if !ok { return }
        process(job)
    }
}
```

**9. Как сделать приоритет одного канала над другим?**
Двойной select: сначала неблокирующая проверка приоритетного канала (select с default), затем общий блокирующий select.

**10. Как добавить таймаут к select?**
Кейс `case <-time.After(d):`. В горячем цикле — `time.NewTimer` с `Reset` вместо `After`.

**11. Как работать с `ticker` в select?**
`case <-ticker.C:` и **обязательно** `defer ticker.Stop()` — иначе утечка таймера.

**12. Что делает `break` внутри select в цикле?**
Выходит только из select, не из for. Нужен label (`break loop`), `return` или флаг.

**13. Как отправить значение с таймаутом?**
```go
select {
case ch <- v: // отправлено
case <-time.After(d): // получатель не успел
}
```
Защита от «отправителя-вечного-ждуна».

**14. Как реализовать «кто первый из N источников»?**
Каждый источник — горутина, пишущая в буферизированный канал; читатель берёт первый результат (select + done). Остальные результаты игнорируются, горутины завершаются по ctx.

## Раздел 13. Пакет sync

**1. Что делает `sync.Mutex`?**
Взаимное исключение: `mu.Lock()` / `mu.Unlock()` — критическая секция исполняется одной горутиной. С Go 1.9 мьютекс «starvation-aware»: долгожданная горутина (ждёт >1 мс) получает лок в порядке очереди.

**2. Почему нельзя копировать мьютекс?**
Копия лока не синхронизирует владельцев. `go vet` ловит «passes lock by value». Структуры с Mutex — всегда по указателю, методы — pointer receiver.

**3. Что даёт `sync.RWMutex`?**
Множество одновременных читателей (`RLock`) или один писатель (`Lock`). Выгоден при read-heavy нагрузке и долгих секциях; на коротких секциях обычный Mutex может быть быстрее из-за накладных расходов.

**4. Тонкости RWMutex?**
Ожидающий писатель блокирует новых читателей (анти-голодание). Рекурсивный `RLock` может дедлокнуть, если между двумя RLock вклинился писатель. RLock-секции завершаются `RUnlock`.

**5. Реентерабелен ли Mutex?**
Нет. Повторный `Lock` в той же горутине — дедлок. Проектируйте код без вложенных локов или с фиксированным порядком захвата.

**6. Что такое `TryLock`?**
Попытка захвата без ожидания (Go 1.18+): полезно для диагностики и оптимистичных сценариев; в обычной бизнес-логике — редкость.

**7. Как работает `sync.WaitGroup`?**
Счётчик: `Add(1)` — до старта горутины, `Done()` — в defer, `Wait()` — дождаться нуля. С Go 1.25: `wg.Go(func(){...})` — сам Add/go/Done.

**8. Типовые ошибки WaitGroup?**
`Add` внутри горутины (гонка с Wait — Wait может проснуться раньше), `Done` без defer (не вызовется при panic), копирование WaitGroup, повторное использование без синхронизации (`Wait` и новый `Add` одновременно).

**9. Что делает `sync.Once`?**
Гарантирует однократное выполнение: ленивая инициализация синглтонов. Внутри — atomic-флаг + мьютекс (double-checked). Повторные вызовы ждут первого завершения.

**10. Что такое `sync.OnceFunc` / `OnceValue` / `OnceValues` (Go 1.21)?**
Обёртки: `f := sync.OnceFunc(func(){ init() })` — f выполняет тело один раз; `OnceValue[T]` кеширует возвращаемое значение; `OnceValues[T1,T2]` — два значения.

**11. Что такое `sync.Pool`?**
Пул временных объектов (`Get`/`Put`), снижает аллокации в горячих путях (буферы, сканеры). Важно: содержимое может быть сброшено в любой GC-цикл; Pool не гарантирует хранение. Инициализация — через поле `New`.

**12. Зачем нужен `sync.Cond`?**
Условная переменная: `Wait` под локом ждёт сигнала, `Broadcast`/`Signal` будят. Редко нужен: чаще выразительнее каналы; Cond полезен при сложных многополярных условиях.

**13. Как устроен `sync.Map`?**
Два слоя: `read` (atomic-доступ без лока) и `dirty` (под мьютексом). Чтение стабильных ключей — lock-free; промахи/записи переносят ключи в dirty. Идеален: кэши, редко меняющийся набор ключей.

**14. Когда `sync.Map` не подходит?**
Частые записи, перекрывающиеся ключи между читателями/писателями, нужны `len`, транзакционность, композитные операции — берите `RWMutex + map`.

**15. Как возникает дедлок на двух мьютексах?**
Горутина A: lock(mu1) → lock(mu2); горутина B: lock(mu2) → lock(mu1). Решение: единый порядок захвата, минимальные секции, отказ от вложенных локов, `TryLock` с откатом.

**16. Атомик или мьютекс?**
Счётчик, флаг, замена указателя на immutable-объект — atomic (дешевле, меньше contention). Инварианты по нескольким полям — мьютекс.

**17. Каноническая защита map с读写?**
```go
type Store struct { mu sync.RWMutex; m map[string]int }
func (s *Store) Get(k string) (int, bool) { s.mu.RLock(); defer s.mu.RUnlock(); v, ok := s.m[k]; return v, ok }
func (s *Store) Set(k string, v int)      { s.mu.Lock(); defer s.mu.Unlock(); s.m[k] = v }
```

**18. Как безопасно обновлять «горячий» конфиг?**
Хранить `atomic.Pointer[Config]`: писатель строит новый immutable-объект и атомарно меняет указатель; читатели без локов видят цельный снапшот.

**19. Почему `defer mu.Unlock()`?**
Паника внутри критической секции не оставит лок захваченным. Unlock вручную — только когда секция сложная и defer мешает.

**20. Как минимизировать критическую секцию?**
Под локом — только чтение/запись данных; копирование и обработку — наружу. Лок на время IO — антипаттерн.

**21. Как сделать семафор?**
`sem := make(chan struct{}, N)`: захват — `sem <- struct{}{}`, освобождение — `<-sem`; или `golang.org/x/sync/semaphore` с весами и контекстом.

**22. Как диагностировать дедлок в проде?**
Профиль goroutine (pprof) — посмотреть, где копятся горутины; block/mutex профили; go tool trace. Рантайм ловит только полный дедлок всех горутин.

**23. Как `go vet` понимает, что структуру с локом копируют?**
Анализ типов: значение содержит `sync.Mutex`/`sync.WaitGroup` (маркер `noCopy`) и копируется — предупреждение. Дополняют поле `_ noCopy` в своих типах.

**24. Mutex против каналов по производительности?**
Mutex — наносекунды при отсутствии конкуренции; каналы дороже, но дают оркестрацию и пайплайны. В очень горячих путях — atomic, RWMutex, шардинг map по ключу.

## Раздел 14. Атомики и модель памяти

**1. Что даёт пакет `sync/atomic`?**
Атомарные операции процессора: `Load`, `Store`, `Add`, `Swap`, `CompareAndSwap`. Гарантируют атомарность и синхронизацию (happens-before) между горутинами.

**2. Что такое `atomic.Value` и `atomic.Pointer[T]`?**
Хранение целого значения/указателя с атомарным чтением-записью. `atomic.Pointer[T]` (Go 1.19) — типизированная версия. Паттерн: immutable-объект целиком меняется одной операцией — читатели всегда видят согласованный снапшот.

**3. Что дают типизированные атомики Go 1.19 (`atomic.Bool`, `atomic.Int64`...)?**
Читаемые имена вместо голых функций, невозможность перепутать типы, корректное выравнивание «из коробки». В новом коде — дефолт.

**4. Когда atomic достаточно без мьютекса?**
Один параметр без связи с соседями: счётчик, флаг остановки, указатель на immutable-конфиг. Как только инвариант охватывает 2+ поля — нужен мьютекс.

**5. Что такое data race по определению Go?**
Две горутины одновременно обращаются к одной ячейке памяти, хотя бы одна — пишет, и нет синхронизации. В Go это undefined behavior: «порванные» значения, фантомные чтения — не просто «чуть неверные числа».

**6. Как ловить гонки?**
`go test -race` / `go build -race` (ThreadSanitizer): находит реальные пересечения доступа. Накладные — кратные к CPU/памяти, поэтому в CI да, в проде — избирательно.

**7. Основные правила happens-before?**
Отправка в канал happens-before соответствующего приёма; `close` — раньше получения нулевого значения; `Unlock` — раньше следующего `Lock`; выход из `Once.Do` — раньше всех его наблюдателей; атомарные операции синхронизируют доступ к этой переменной.

**8. Пример гонки и корректных фиксов?**
`counter++` из двух горутин теряет инкременты (чтение-модификация-запись не атомарна). Фиксы: `atomic.Int64.Add`, `sync.Mutex`, либо владелец-горутина, которая одна меняет переменную, получая команды по каналу.

**9. Как безопасно «опубликовать» объект другим горутинам?**
Собрать объект полностью → атомарный `Store` в `atomic.Pointer`, запись под локом, или передача через канал. Тогда читатель видит либо старый, либо новый полный объект — без «недостроенных».

**10. Что такое torn read и при чём тут 32-бит платформы?**
64-битное значение читается двумя 32-битными операциями — можно получить половину старого + половину нового. Атомики решают; типизированные (`atomic.Int64`) сами обеспечивают выравнивание.

**11. Что такое false sharing?**
Две независимые переменные попали в одну кэш-линию, их пишут разные ядра — линия постоянно инвалидизируется. Лечение — разнесение по линиям (padding) в экстремально горячем коде.

**12. Есть ли в Go параметры memory ordering, как в C++?**
Нет: все атомики последовательной согласованности (seq-cst). Меньше вариантов — меньше ошибок; для прикладного Go этого достаточно.

**13. Чем опасна гонка на срезе/строке/интерфейсе?**
Это многозначные заголовки (срез — 3 слова). Конкурентная запись «одного элемента» может порвать заголовок — получить невалидный указатель. Защищать весь заголовок: мьютекс или `atomic.Value`.

**14. Как считать высокочастотную метрику?**
Локальные аккумуляторы на горутину (обычные переменные) + редкое слияние под локом/атомиком. Глобальный atomic-счётчик на каждый инкремент при большой конкуренции кэшится плохо.

**15. Как документировать потокобезопасность типа?**
Комментарий к типу: «safe for concurrent use» (как `sql.DB`) или «не thread-safe, синхронизируйте снаружи» (как большинство коллекций). Это часть API.

**16. Есть ли в Go `volatile`?**
Нет. Видимость изменений между горутинами обеспечивают только атомики, каналы, мьютексы и `Once` — обычное чтение/запись оптимизируются компилятором свободно.

## Раздел 15. Context

**1. Что такое `context.Context`?**
Стандартный способ передачи отмены, дедлайнов и request-scoped значений через цепочку вызовов. Интерфейс: `Deadline()`, `Done() <-chan struct{}`, `Err()`, `Value(key)`.

**2. `context.Background()` против `context.TODO()`?**
`Background` — корень: main, серверы, тесты. `TODO` — то же значение, но маркер «место не определили, заменить позже».

**3. Как работает `WithCancel`?**
```go
ctx, cancel := context.WithCancel(parent)
defer cancel() // освобождает ресурсы и детей
```
Отмена — закрытие `Done()`. Всегда вызывать cancel (повторный вызов безопасен).

**4. Что делают `WithTimeout` и `WithDeadline`?**
Автоотмена по времени: `ctx, cancel := context.WithTimeout(ctx, 3*time.Second)`. `defer cancel()` освобождает таймер раньше — без этого таймер живёт до срабатывания.

**5. Как наследуются отмены?**
Отмена родителя отменяет всех потомков; отмена ребёнка — нет. Дедлайн ребёнка не может быть позже родительского (эффективно берётся минимальный).

**6. Где проверять отмену?**
В циклах и перед «дорогими» шагами: `select { case <-ctx.Done(): return ctx.Err(); default: }` или после блокирующих операций `ctx.Err()`. Чистая CPU-функция сама не прервётся — проверки на границах.

**7. Правила `WithValue`?**
Ключ — собственный непубличный тип: `type ctxKey struct{}`. Только request-scoped данные (trace-id, auth). Бизнес-параметры — аргументы функций, а не контекст.

**8. Соглашения передачи контекста?**
Первый параметр `ctx context.Context`; не хранить в полях структур (кроме типов-носителей запроса); пробрасывать дальше в вызовы.

**9. Как реагирует горутина на отмену?**
Внутри цикла работы select с `ctx.Done()`; по отмене — аккуратно завершиться и вернуть `ctx.Err()`.

**10. Что проверяет vet по контекстам (lostcancel)?**
Что cancel, возвращённый WithCancel/WithTimeout, не потерян — иначе таймер/регистрация живут дольше нужного (утечка).

**11. Как контекст работает с БД?**
`QueryContext`, `ExecContext`, `BeginTx`: отмена прокидывается в драйвер — для PostgreSQL запрос реально прерывается на сервере.

**12. Контекст и HTTP?**
Сервер: `r.Context()` отменяется при разрыве соединения клиентом. Клиент: `req.WithContext(ctx)` плюс `http.Client.Timeout` для ограничения всей операции.

**13. Какие значения возвращает `ctx.Err()`?**
`context.Canceled` (ручная отмена) или `context.DeadlineExceeded` (таймаут/дедлайн). Проверять через `errors.Is`.

**14. Как передать отмену в выполняемую горутину?**
Сам контекст: горутина держит `ctx` и select'ит `ctx.Done()`. Закрытие done-канала — механизм доставки.

**15. Что нового появилось в пакете context?**
`WithCancelCause` (Go 1.20) — отмена с причиной, читается через `context.Cause(ctx)`; `AfterFunc(ctx, f)` — колбэк по отмене (Go 1.21); `WithoutCancel` (Go 1.21) — контекст без наследования отмены родителя (для фоновых задач типа аудита); `WithDeadlineCause`/`WithTimeoutCause` (Go 1.21) — причина у дедлайна.

**16. Топ антипаттернов context?**
Хранение в структуре, бизнес-данные через `WithValue`, игнорирование `Done()`, передача `nil` (нужен `TODO()`), отсутствие `defer cancel()`, контекст запроса, «протёкший» в долгоживущую фоновую задачу без `WithoutCancel`.

## Раздел 16. Планировщик (модель GMP)

**1. Из чего состоит модель GMP?**
G — горутина (стек, состояние, ссылка на инструкцию). M — поток ОС. P — логический процессор: контекст выполнения с локальной очередью горутин; их число = `GOMAXPROCS`. Горутины исполняются только на M, привязанном к P.

**2. Зачем нужен P, если есть M?**
P отделяет «логику планирования» от потоков ОС: держит локальную очередь и кэши (аллокатор mcache, сегменты стека), уменьшая contention на глобальную очередь. M без P — спит или блокирован.

**3. Как устроены очереди и work stealing?**
Локальная очередь на P (~256 элементов) + глобальная очередь. Освободившийся P сначала берёт из runnext/локальной, затем — крадёт половину очереди у случайного соседа, затем проверяет глобальную.

**4. Что происходит при блокирующем syscall?**
M уходит в syscall вместе с заблокированной G; планировщик отдаёт освободившийся P другому M (парковому или новому). По возвращении M пытается вернуть P, иначе паркуется. Так процессор не простаивает из-за IO в старых библиотеках.

**5. Как обрабатывается сетевой I/O?**
Через netpoller (epoll/kqueue/IOCP): горутина, ждущая сеть, паркуется, M свободен; при готовности дескриптора G возвращается в очередь. Поэтому сетевые горутины не «съедают» потоки ОС.

**6. Как работает вытеснение горутин?**
Кооперативные точки: вызовы функций, аллокации, операции с каналами. С Go 1.14 добавлено асинхронное вытеснение сигналом: sysmon прерывает горутину, работающую дольше ~10 мс, даже без вызовов — «жёсткий» цикл больше не голодает соседей.

**7. Почему горутины такие дешёвые?**
Маленький стартовый стек (2 КБ) с копирующим ростом, быстрое переключение в user-space (без syscalls), пул потоков M. Поток ОС — мегабайты стека и дорогой switch ядра.

**8. Что такое слот runnext?**
Одно место на P для самой свежей «готовой» G: повышает локальность кэша при коротких цепочках «запустил — сразу продолжил».

**9. Что происходит с лишними M?**
Паркуются (спят) в пуле потоков; просыпаются по мере появления работы. Потоки создаются при нехватке, уничтожаются редко.

**10. Даёт ли планировщик реальные гарантии времени?**
Нет: это не RT-планировщик — нет приоритетов и дедлайнов. Для жёстких требований по латентности Go не подходит на уровне ОС-гарантий.

**11. Что будет при активном busy-loop в горутине?**
До 1.14 — голодание соседей на том же P. Сейчас — асинхронное вытеснение, но пустой спин всё равно тратит CPU: правильное решение — синхронизация (каналы/условные переменные), а не ожидание циклом.

**12. Зачем `runtime.LockOSThread()`?**
Прикрепляет текущую G к текущему M навсегда: нужен для кода с thread-local состоянием (GUI, CGO-библиотеки, some audio stacks).

**13. Как диагностировать планировщик?**
`GODEBUG=schedtrace=1000` (снимки очередей), `scheddetail=1`; профиль goroutine; `go tool trace` — таймлайн выполнения, GC, блокировки.

**14. Как часто проверяется глобальная очередь?**
Каждый 61-й тик планировщик сначала заглядывает в глобальную очередь — защита от её голодания.

**15. Что меняется при `GOMAXPROCS(1)`?**
Один P: горутины строго по очереди — удобный режим отладки кооперативных дедлоков и понимания «параллельность ≠ конкурентность».

**16. Как GOMAXPROCS ведёт себя в контейнерах?**
Раньше — всегда NumCPU ноды, что при CPU-лимите контейнера давало oversubscription (лечили automaxprocs). С Go 1.25 рантайм читает cgroup-лимиты сам.

## Раздел 17. Сборщик мусора и утечки памяти

**1. Какой GC в Go?**
Параллельно-конкурентный mark-and-sweep с тройной раскраской (tricolor) и гибридным write barrier. Не генерационный, не компактирующий. Ставка — короткие паузы, а не максимальный throughput.

**2. Фазы GC и длина пауз?**
Короткий STW на старте маркировки → конкурентная маркировка вместе с приложением → короткий STW mark termination → конкурентная очистка. Паузы обычно доли миллисекунды.

**3. Суть tricolor-маркировки?**
Белые — не найдены (кандидаты на сбор), серые — найдены, но дети не проверены, чёрные — обработаны. Write barrier не даёт «потерять» живой объект при конкурентной работе приложения.

**4. Что настраивает GOGC?**
Целевой рост heap между GC: `GOGC=100` (дефолт) — новый GC, когда heap вырос вдвое относительно живой памяти. Больше GOGC — реже GC, больше память; меньше — чаще GC, меньше память.

**5. Что такое GOMEMLIMIT (Go 1.19)?**
Soft-лимит суммарной памяти рантайма. Позволяет включить режим «вписаться в лимит» (часто с `GOGC=off`) для контейнеров: GC ускоряется при приближении к лимиту. Аккуратно: при невозможности удержать лимит — OOM kill.

**6. Почему GC не компактирующий и что из этого следует?**
Компактация сложна в конкурентном режиме; Go выбрал короткие паузы. Следствие — возможная фрагментация и то, что долгоживущие данные не «переезжают».

**7. Что на самом деле собирает GC?**
Недостижимое из корней (стеки горутин, глобальные переменные). «Утечка» в Go — это достижимое, но ненужное: висящие горутины, глобальные кэши, таймеры, отложенные ссылки.

**8. Топовые утечки памяти на практике?**
`time.Ticker` без `Stop`; `time.After` в цикле; подстрока/подсрез держит огромный underlying-массив; утечка горутин; неограниченный map-кэш без TTL; незакрытые ресурсы (rows, body).

**9. Как найти утечку горутин?**
Два снимка `pprof goroutine` с интервалом — если число и стопки растут, ищем место. В тестах — `goleak`. Метрика `NumGoroutine` в мониторинге.

**10. Как читать heap-профиль: inuse vs alloc?**
`inuse_objects/inuse_space` — что занимает память сейчас (утечки); `alloc_objects/alloc_space` — что аллоцировалось за всё время (нагрузка на GC). Смотреть оба.

**11. Что даёт `runtime.ReadMemStats`?**
Снимок памяти: `HeapAlloc`, `HeapSys`, `Sys`, `NumGC`, паузы. Для метрик; вызов дорогой (короткий STW) — не в горячем цикле.

**12. Чем управлять GC из кода?**
`debug.SetGCPercent(n)`, `debug.SetMemoryLimit(b)`; `debug.FreeOSMemory()` — форс GC + возврат памяти ОС (после пиковых нагрузок).

**13. Почему структуры без указателей дружелюбнее к GC?**
Mark должен обходить поля-указатели. `[]int` — один блок памяти без обхода; `[]*T` — n указателей + n объектов. Меньше указателей → быстрее маркировка.

**14. Как sync.Pool связан с GC?**
Объекты пула могут быть удалены при каждом GC — Pool годится только для «горячего» переиспользования между GC-циклами, не для хранения.

**15. Как увидеть, что уходит в heap?**
`go build -gcflags='-m'` — вывод escape-анализа: возврат указателя, сохранение в интерфейс, большие объекты, замыкания.

**16. Как посмотреть работу GC в проде?**
`GODEBUG=gctrace=1` — строка на каждый GC: объёмы, паузы, причины. Плюс метрики рантайма (экспортёры вида prometheus client_golang).

**17. Почему финализаторы — плохой механизм очистки?**
`runtime.SetFinalizer` срабатывает недетерминированно, продлевает жизнь объекта (два цикла GC), легко пропустить. Освобождение — только явное `Close()`/`ctx.Done()`.

**18. Что делает builtin `clear`?**
`clear(map)` — удалить все ключи (без реаллокации), `clear(slice)` — занулить элементы. Удобно для переиспользования буферов и map.

## Раздел 18. Конкурентные паттерны

**1. Канонический worker pool?**
```go
jobs := make(chan Job); results := make(chan Result)
var wg sync.WaitGroup
for i := 0; i < workers; i++ {
    wg.Add(1)
    go func() { defer wg.Done(); for j := range jobs { results <- process(j) } }()
}
go func() { wg.Wait(); close(results) }()
```
Фиксированная параллельность, выход через закрытие каналов.

**2. Паттерн pipeline?**
Стадии: генератор → обработчики → потребитель. Каждая стадия — горутина с входным и выходным каналом; отмена — ctx; каждая стадия обязана слушать `ctx.Done()` при отправке.

**3. Что такое fan-out и fan-in?**
Fan-out — несколько воркеров читают один входной канал (масштабирование обработки). Fan-in — слияние нескольких выходных каналов в один (WaitGroup + close по завершении всех).

**4. Как реализовать семафор?**
`sem := make(chan struct{}, N)` — буфер ограничивает параллелизм; или `x/sync/semaphore` с весами и контекстом (отменяемое ожидание).

**5. Как ограничить частоту (rate limiting)?**
`golang.org/x/time/rate`: `Limiter.Wait(ctx)` (блокирующе), `Allow()` (сейчас/нет). Для per-key — map ключ→лимитер; глобальный лимит + локальные бакеты.

**6. Канонический graceful shutdown?**
`signal.NotifyContext(ctx, os.Interrupt, syscall.SIGTERM)` → перестать принимать новые задачи → дать текущим завершиться с таймаутом (`srv.Shutdown`, drain очереди) → закрыть ресурсы (БД, брокер) → exit.

**7. Паттерн «генератор» (producer)?**
Функция возвращает `<-chan T`; внутри горутина наполняет и `close(out)` по завершении; при отправке — select с `ctx.Done()`.

**8. Что такое or-done?**
Обёртка над чтением канала с учётом отмены:
```go
func orDone(ctx context.Context, ch <-chan T) <-chan T { ... }
```
Позволяет читать в range, не думая об отмене, — отмена «встраивается» в поток.

**9. Что такое or-channel?**
Слияние N каналов завершения в один: «завершиться, когда любой из них завершится». Реализуется рекурсивной горутиной поверх select.

**10. Паттерн future/promise?**
```go
func async[T any](f func() T) <-chan T {
    ch := make(chan T, 1)
    go func() { ch <- f() }()
    return ch
}
```
Буфер 1 — горутина не блокируется, результат «готов к чтению».

**11. Что делать с результатом, если потребитель уже ушёл?**
Отправка в select с `ctx.Done()`/done-каналом: `select { case res <- result: case <-ctx.Done(): }`. Буфер 1 у результата — тоже типовое решение.

**12. Почему параллелизм всегда надо ограничивать?**
Неограниченные горутины на каждый запрос → OOM и взаимные блокировки под нагрузкой. Инструменты: пул воркеров, `errgroup.SetLimit`, канал-семафор, ограничение очереди с 429.

**13. Как передавать ошибку из конкурентного потока?**
Значением в канале: `type Result struct { Value T; Err error }`. Ошибка — значение; потребитель решает, что делать (errgroup автоматизирует «первую ошибку + отмену»).

**14. Что такое heartbeat в пайплайне?**
Воркер периодически пингует «жив» (в канал/метрику) — позволяет отличить медленную работу от зависания и построить мониторинг стадий.

## Раздел 19. Дженерики

**1. Базовый синтаксис дженериков?**
```go
func Map[T, U any](s []T, f func(T) U) []U { ... }
```
Типовые параметры в квадратных скобках; типы аргументов обычно выводятся автоматически.

**2. Что такое ограничения (constraints)?**
Интерфейсы, описывающие допустимые типы: `any`, `comparable`, интерфейсы с методами, объединения: `type Number interface { ~int | ~int64 | ~float64 }`.

**3. Что означает `~` в ограничении?**
«Все типы с этим underlying-типом»: `~int` покрывает `type MyInt int`, а не только сам `int`.

**4. Как жили до дженериков (1.18)?**
`interface{}` + type assertions, рефлексия, кодогенерация (`go:generate`). Дженерики закрыли основную часть этого кода.

**5. Можно ли объявить дженерик-метод?**
Нет: методы не могут иметь собственных типовых параметров. Дженериками могут быть типы и функции.

**6. Как выглядит дженерик-структура?**
```go
type Stack[T any] struct { items []T }
func (s *Stack[T]) Push(v T) { s.items = append(s.items, v) }
```
Инстанциирование: `Stack[int]`, `Stack[User]`.

**7. Как дженерики компилируются?**
GCShape-стенсилинг: типы одинаковой «формы» (например, все указатели) разделяют один сгенерированный код + словари с метаданными. Это не полный мономорфизм — есть небольшой диспетчеризационный overhead.

**8. Что даёт ограничение `comparable`?**
Требует поддержки `==`/`!=` — например, для ключей map внутри дженерик-функции. Срезы/map/функции компилятор отсечёт.

**9. Какие пакеты стандартной библиотеки построены на дженериках?**
`slices` (Sort, Contains, Index, Clone...), `maps` (утилиты; состав функций менялся между 1.21–1.23 — `maps.Keys` с 1.23 возвращает итератор).

**10. Дженерики vs интерфейсы — критерии выбора?**
Дженерики: одинаковый алгоритм для разных типов, без боксинга, с типобезопасностью на компиляции. Интерфейсы: разнотипные значения в одной коллекции, динамическая диспетчеризация, DI, plugin-стиль.

**11. Ограничения текущей реализации?**
Нет дженерик-методов, нет частичной специализации, иногда невнятные ошибки компиляции, нет дефолтных типов в ограничениях-интерфейсах.

**12. Подводный камень с float и comparable?**
`NaN != NaN`: поиск «равного» float в слайсе/map не найдёт NaN. Для ключей и сравнений — аккуратность.

**13. Когда дженерики не нужны?**
Один-два конкретных типа (concrete-код проще), нужна динамика типов (интерфейсы), или обобщения усложняют чтение. Не писать «template-библиотеки» ради дженериков.

**14. Ограничение с методами — как использовать?**
```go
type Stringer interface { String() string }
func Join[T Stringer](xs []T) string { /* можно вызывать x.String() */ }
```
Внутри функции доступны только операции, обещанные ограничением.

## Раздел 20. Тестирование

**1. Минимальный тест?**
Файл `foo_test.go`, функция `func TestSum(t *testing.T)`, запуск `go test ./...`. Имена только `TestXxx` с большой буквы.

**2. Канонический table-driven тест?**
```go
tests := []struct{ name string; in string; want int; wantErr error }{...}
for _, tt := range tests {
    t.Run(tt.name, func(t *testing.T) {
        got, err := Parse(tt.in)
        require.ErrorIs(t, err, tt.wantErr)
        require.Equal(t, tt.want, got)
    })
}
```

**3. `t.Error` против `t.Fatal`?**
`Error` — зафиксировать проблему и продолжить; `Fatal` — немедленно прекратить текущий тест. В под-тестах `Fatal` не останавливает родителя и остальные под-тесты.

**4. Как работает `t.Parallel`?**
Помечает тест/под-тест параллельным — выполняется одновременно с другими. До Go 1.22 обязательно захватывать переменную цикла (`tt := tt`) до вызова.

**5. Что делает `t.Cleanup`?**
Регистрирует функцию уборки (аналог defer для теста) — вызывается по завершении, даже при `t.Fatal`. Удобно для временных ресурсов, БД, серверов.

**6. Зачем `t.Helper()`?**
Помечает функцию-помощник: при ошибке трейс указывает на место вызова в тесте, а не внутрь хелпера.

**7. Что даёт `t.TempDir()`?**
Временная директория с автоматической очисткой после теста — для файловых сценариев.

**8. Подходы к мокам в Go?**
Интерфейс + ручной фейк/стаб (идиоматично), кодогенерация (mockery, gomock), testify/mock. Начинать с простых фейков: меньше магии и зависимостей.

**9. Как тестировать HTTP-хендлеры?**
`httptest.NewRecorder()` + прямой вызов хендлера — быстрый unit-тест; `httptest.NewServer` — интеграционный с реальной сетью.

**10. Как тестировать HTTP-клиент?**
`httptest.NewServer` поднимает локальный сервер-заглушку, клиент настраивается на его URL; проверяются запросы, заголовки, обработка ошибок.

**11. Зачем `-race` в тестах?**
Находит data races в конкурентном коде. Обязателен в CI: гонки без него почти не воспроизводятся, а последствия — undefined behavior.

**12. Как мерить покрытие?**
`go test -cover -coverprofile=cover.out`; `go tool cover -html=cover.out`. Покрытие — индикатор дыр, не цель.

**13. Что такое `TestMain`?**
`func TestMain(m *testing.M)` — setup/teardown на весь пакет; в конце обязательно `os.Exit(m.Run())`.

**14. Что такое fuzzing (Go 1.18)?**
`func FuzzParse(f *testing.F)`: сиды через `f.Add`, затем `f.Fuzz(func(t, input string){...})` — автоматический поиск крашей на случайных входах.

**15. Как тестировать приватные функции?**
Тесты в том же пакете (`package foo`) видят неэкспортируемое. `package foo_test` — внешний взгляд: тестировать только публичный API.

**16. Как тестировать код, зависящий от времени?**
Инъекция: интерфейс `Clock` или переменная-функция `now = time.Now` в структуре; тест подставляет фиксированное/двигаемое время.

**17. Как тестировать конкурентный код?**
`-race`, синхронизация через каналы/WaitGroup, проверки с таймаутами (select + time.After), специальные тесты дедлоков, `goleak` после тестов.

**18. Testify: assert vs require?**
`assert` — проверка и продолжение; `require` — проверка и немедленный провал теста. В suite — общие setup/teardown. Стандартная библиотека без зависимостей тоже приемлема — вопрос стиля команды.

**19. Что такое golden files?**
Эталонные файлы с ожидаемым выводом: тест сравнивает, флаг `-update` перегенерирует. Для сложных структур (рендеры, большие JSON).

**20. Как отделять интеграционные тесты?**
Build-теги `//go:build integration`, тест-контейнеры (testcontainers-go) или docker-compose в CI; отдельный шаг пайплайна.

**21. Как проверить, что функция паникует?**
`assert.Panics`/`require.Panics` или собственный defer/recover в тесте. Для ожидаемых ошибок — panic не использовать вовсе.

**22. Зачем goleak?**
`uber-go/goleak` в TestMain проверяет, что после тестов не осталось горутин — ловит утечки и забытые фоновые задачи.

## Раздел 21. Бенчмарки и профилирование

**1. Как пишется бенчмарк?**
```go
func BenchmarkSum(b *testing.B) {
    for i := 0; i < b.N; i++ { Sum(xs) }
}
// go test -bench=. -benchmem
```
С Go 1.24 — `for b.Loop() {}` (авто-timer, стабильные итерации).

**2. Зачем `b.ResetTimer` / `StopTimer` / `StartTimer`?**
Отсечь подготовку (генерация данных, setup) из измерения: ResetTimer обнуляет счётчик после setup; Stop/Start — для исключения кусков внутри цикла.

**3. Что показывают `-benchmem` метрики?**
`B/op` — байт на операцию, `allocs/op` — аллокаций на операцию. Мусор для GC часто важнее наносекунд.

**4. Что даёт `b.Run`?**
Суб-бенчмарки: сравнение вариантов в одном прогоне (`b.Run("naive", ...)` vs `b.Run("fast", ...)`), с параметризацией по размеру входа.

**5. Зачем benchstat?**
Статистическое сравнение двух наборов прогонов: «+3.1% ± 0.5%» вместо «кажется быстрее». Убирает шум машины.

**6. Как снять CPU-профиль?**
`go test -cpuprofile=cpu.out` или `pprof.StartCPUProfile` в коде. Анализ: `go tool pprof cpu.out` → `-top`, `-list func`, flame graph (`-http`).

**7. Как читать heap-профиль?**
`-inuse_space` — текущая память (утечки), `-alloc_space` — суммарные аллокации (нагрузка на GC). Фильтры по объектам/размерам в pprof-интерфейсе.

**8. Как профилировать живой сервис?**
`import _ "net/http/pprof"` на внутреннем порту: снимки CPU/heap/goroutine/block/mutex на реальном трафике без остановки.

**9. Что даёт flame graph?**
Иерархию стека: ширина блока — доля CPU. Сразу видно горячие пути и глубину стека; `go tool pprof -http=:8080` строит интерактивно.

**10. Что показывает execution trace?**
`go tool trace`: таймлайн горутин, блокировки, GC-паузы, работа планировщика во времени — то, чего нет в агрегированных профилях.

**11. Типовые снижения аллокаций?**
Предаллокация (`make` с cap), `sync.Pool` для буферов, значения вместо указателей в горячих структурах, `strings.Builder`, переиспользование объектов, избегание конверсий `[]byte<->string`.

**12. Ловушки микробенчмарков?**
Компилятор выбрасывает неиспользуемый результат (нужен sink), шум ОС/турбобуста, слишком мало итераций, бенч не в том контексте (кэш прогрет иначе, чем в проде).

**13. Как мерить латентность сервиса (p99)?**
Гистограммы в метриках (Prometheus), не бенчмарки: `rate`, `histogram_quantile` по перцентилям. Бенчи — для кода, метрики — для сервиса.

**14. Классический пример оптимизации — конкатенация строк?**
`s += part` в цикле — O(n²) (новая строка каждый раз); `strings.Builder.WriteString` — амортизированно O(n). Разница на порядках, видна в `allocs/op`.

## Раздел 22. io и стандартная библиотека

**1. Контракт `io.Reader`?**
`Read(p []byte) (n int, err error)`: читает до len(p) байт, возвращает число прочитанных и ошибку. `io.EOF` — штатный конец данных. Допустимо `n > 0 && err == io.EOF` одновременно.

**2. Контракт `io.Writer`?**
`Write(p []byte) (n int, err error)`: если `n < len(p)` — обязательно вернуть ошибку. Пишущий код обязан проверять n и err.

**3. Что делает `io.Copy`?**
Копирует src → dst через внутренний буфер (32 КБ); использует оптимизации `ReaderFrom`/`WriterTo`, если реализованы. Потоковое копирование без загрузки всего в память.

**4. Когда можно `io.ReadAll`?**
Только для заведомо маленьких данных (конфиг, маленький ответ). На сети/файлах произвольного размера — риск OOM; использовать `io.Copy`/стриминг.

**5. Полезные обёртки io?**
`LimitReader` (лимит), `MultiReader` (склейка), `TeeReader` (чтение + копия в writer), `io.Pipe` (синхронная труба), `NopCloser`, `io.Discard`.

**6. Подводный камень `bufio.Scanner`?**
Лимит строки по умолчанию 64 КБ — большие строки дают ошибку `token too long`; расширять: `scanner.Buffer(buf, max)`. Сканер одноразовый; ошибки проверять `scanner.Err()`.

**7. Что важно при `bufio.Writer`?**
Обязательно `Flush` в конце (иначе часть данных останется в буфере); ошибку Flush проверять — это последняя реальная запись на диск.

**8. `bytes.Buffer` против `strings.Builder`?**
Buffer — мутабельный байтовый буфер, реализует Reader/Writer (можно читать из него). Builder — только сборка строк: меньше абстракции и аллокаций для чистой конкатенации.

**9. Как закрывать файлы корректно?**
`defer f.Close()`; при записи — проверять и ошибку `Close` (данные могут не долиться в диск из буферов ОС).

**10. Что такое `io/fs` и `embed`?**
`io/fs` — абстракция файловой системы (`fs.FS`), поверх которой работают пакеты. `//go:embed` — встраивание файлов в бинарник, доступ через `embed.FS`.

**11. Чем `io.ErrUnexpectedEOF` отличается от `io.EOF`?**
`EOF` — штатный конец; `UnexpectedEOF` — данные оборвались посреди структуры (недочитанное сообщение, декодер). Различать обязательно: Unexpected — ошибка протокола.

**12. Как читать большие данные из сети?**
Потоково: `io.Copy` в файл/хеш-сумматор, `bufio.Scanner` для строк, декодер JSON поверх body. Никаких `ReadAll` без лимита.

**13. Для чего `io.Pipe`?**
Синхронная in-memory труба: writer пишет, reader читает одновременно — например, архив на лету в HTTP-ответ без промежуточного файла.

**14. Кто должен закрывать `io.ReadCloser`, переданный в функцию?**
Владелец — тот, кто открыл. Функции, принимающие `io.Reader`, не закрывают; контракт фиксировать в документации.

**15. Как ограничить чтение HTTP-тела?**
`http.MaxBytesReader(w, r.Body, limit)` — возвращает ошибку при превышении (и сообщает об этом серверу); либо `io.LimitReader` + проверка, что прочитали меньше лимита.

**16. Пайплайн «читаем-обрабатываем-пишем»?**
`Scanner` (строки) → обработка → `bufio.Writer`; после цикла — `scanner.Err()` и `w.Flush()`. Ошибки каждого этапа обрабатываются отдельно; буферы — переиспользовать.

## Раздел 23. JSON и сериализация

**1. Основные теги encoding/json?**
`json:"name"` — имя поля; `omitempty` — пропуск нулевых значений; `-` — исключить поле; `,string` — число как строка; `json:"name,omitempty"` — комбинируются через запятую.

**2. Чем nil-срез отличается от пустого в JSON?**
nil → `null`, `[]T{}` → `[]`. Для стабильных API-контрактов пустые слайсы инициализируют явно, чтобы клиенты не ломались на null.

**3. Зачем указатели в полях структур?**
`*int` различает «поле отсутствует/null» и «значение 0»; вместе с `omitempty` не сериализуется при nil. Стандарт для PATCH-запросов и опциональных полей.

**4. Что будет при `Unmarshal` в `interface{}`?**
Числа станут `float64` (потеря точности на больших int64!), объекты — `map[string]any`, массивы — `[]any`. Решение: `json.Decoder.UseNumber()`.

**5. Что такое `json.Number`?**
Строка, представляющая число без потери точности; методы `Int64()`, `Float64()`. Используется при `UseNumber` для больших чисел/идентификаторов.

**6. Как разбирать динамический JSON, у которого поле бывает двух типов?**
Два прохода: сначала в структуру с `json.RawMessage` полем, затем разбор RawMessage по фактическому виду. RawMessage — «отложенный» кусок сырого JSON.

**7. Как сделать кастомную сериализацию?**
Методы `MarshalJSON() ([]byte, error)` и `UnmarshalJSON([]byte) error`. Применение: нестандартные форматы дат, enum-строки, wrapper-типы. В UnmarshalJSON помнить о разборе в тип-псевдоним, чтобы не зациклиться.

**8. Encoder/Decoder против Marshal/Unmarshal?**
Encoder/Decoder — стриминг: последовательности объектов, большие данные, работа с io.Reader/Writer; у Encoder есть `SetEscapeHTML(false)`. Marshal/Unmarshal — разовая работа с байтами.

**9. Как сериализуется `time.Time`?**
RFC 3339 (`2024-01-02T15:04:05Z07:00`) автоматически. Другой формат — тип-обёртка с кастомным (Un)MarshalJSON.

**10. В каком порядке идут ключи в выводе?**
Структура — в порядке объявления полей; map — отсортированы по ключу. Вывод детерминированный (важно для golden-тестов и кэшей).

**11. Как embedding влияет на JSON?**
Анонимные поля «разворачиваются» в родителя (плоский JSON), если нет конфликта имён; конфликтные поля игнорируются.

**12. Как валидировать вход после Unmarshal?**
Ручные проверки (часто + `errors.Join`), теги `validate` через go-playground/validator, кастомный UnmarshalJSON с проверками на этапе разбора.

**13. Что делать, если encoding/json стал узким местом?**
Профиль → замена на быструю библиотеку (easyjson — кодогенерация, sonic — SIMD, jsoniter) или переход на proto. Сначала измерить, потом менять.

**14. Как дебажить ошибки Unmarshal?**
`*json.UnmarshalTypeError` содержит поле и тип; `*json.SyntaxError` — offset в байтах. Логировать поле/offset, писать тест с проблемным payload.

**15. YAML/TOML/protobuf — когда что?**
YAML (gopkg.in/yaml.v3) — конфиги; TOML — конфиги без вложенности-ада; protobuf — контракты сервисов и gRPC; JSON — API и интеграции.

**16. Как сделать частичное обновление структуры из JSON?**
Указатели на поля (nil = не прислали) или разбор в `map[string]any` с выборочным применением. Для строгих API — PATCH-DTO с указателями.

## Раздел 24. HTTP: сервер и клиент

**1. Минимальный HTTP-сервер?**
```go
http.HandleFunc("/health", func(w http.ResponseWriter, r *http.Request) { w.WriteHeader(http.StatusOK) })
srv := &http.Server{Addr: ":8080", ReadHeaderTimeout: 5 * time.Second}
srv.ListenAndServe()
```
Явный `http.Server` — обязательно, чтобы задать таймауты.

**2. Что такое `http.Handler` и `http.HandlerFunc`?**
Интерфейс с `ServeHTTP(w, r)` и адаптер: именованный тип функции с этим методом. `func(w,r)` → `http.HandlerFunc(f)` → Handler.

**3. Что умеет встроенный роутер с Go 1.22?**
Паттерны с методом и параметрами: `"GET /users/{id}"`, значение — `r.PathValue("id")`; `{$}` — точное совпадение корня; автоматическая обработка trailing slash. Для многих API больше не нужен сторонний роутер.

**4. Как пишется middleware?**
`func(next http.Handler) http.Handler` — обёртка: что-то до/после `next.ServeHTTP`. Цепочка собирается композицией. Типовые: recover, логи, метрики, auth, tracing.

**5. Как читать тело запроса?**
`json.NewDecoder(r.Body).Decode(&v)` или `io.ReadAll` с лимитом. Body — `ReadCloser`: прочитать/закрыть обязательно для keep-alive соединения.

**6. Как ограничить размер тела?**
`http.MaxBytesReader(w, r.Body, n)` — ошибка при превышении; иначе DoS через большой payload.

**7. Как формировать ответ?**
`w.Header().Set("Content-Type", "application/json")` до записи; `w.WriteHeader(status)` — один раз и до первого `Write`; дальше — `w.Write(...)`/`json.NewEncoder(w).Encode(v)`.

**8. Что делает `http.Error`?**
Ставит Content-Type text/plain, пишет статус и сообщение. Для JSON-ошибок — свой хелпер с единым форматом.

**9. Какие таймауты обязан иметь сервер?**
`ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout`, `IdleTimeout`. Без них — slow-loris и накопление зависших соединений.

**10. Как сделать graceful shutdown?**
По сигналу — `srv.Shutdown(ctx)` (дожидается активных запросов) с таймаутом; если не уложились — `srv.Close()`. Сначала закрыть приём новых соединений (балансировщик отводит трафик).

**11. Чем опасен `http.DefaultClient`?**
Ноль таймаутов: запрос может висеть вечно. Всегда свой `http.Client{Timeout: ...}` или контекстный таймаут на запрос.

**12. Как настроить переиспользование соединений у клиента?**
Свой `http.Transport`: `MaxIdleConns`, `MaxIdleConnsPerHost`, `IdleConnTimeout`. Один Transport на приложение (он потокобезопасен), не создавать Client на каждый запрос.

**13. Как контролировать редиректы клиента?**
`CheckRedirect` в `http.Client`: вернуть `http.ErrUseLastResponse` — не следовать; иначе ограничить число/проверять адреса (SSRF-защита).

**14. Как поставить/прочитать cookie?**
`http.SetCookie(w, &http.Cookie{Name, Value, Path, MaxAge, Secure, HttpOnly})`; чтение — `r.Cookie("name")`.

**15. Как принимать загрузки файлов?**
`r.ParseMultipartForm(limit)` + `r.FormFile("file")`, либо стриминг через `multipart.Reader` для больших файлов — без загрузки всего в память.

**16. Как написать reverse proxy?**
`httputil.NewSingleHostReverseProxy(target)` + модификация директора (заголовки, таймауты). Для кэширующих/агрегирующих прокси — свои handler'ы.

**17. Какой стек для WebSocket?**
Апгрейд соединения: gorilla/websocket или coder/websocket (бывший nhooyr). Стандартная библиотека умеет только hijack — WS-протокол поверх — библиотека.

**18. Какие статусы типовой Go-API отдаёт?**
200/201/204 успех; 400 валидация, 401/403 аутентификация/права, 404, 409 конфликт, 422 семантика, 429 лимит; 500 внутренние. Ошибка в теле при статусе 200 — антипаттерн.

**19. Как узнать реальный статус-код в middleware?**
Обёртка ResponseWriter, перехватывающая `WriteHeader` (интерфейс с полями status, bytes). Для метрик и логов — стандартный приём.

**20. Как определять IP клиента за прокси?**
`X-Forwarded-For`/`X-Real-IP` — но доверять только заголовкам от собственного балансировщика; иначе клиент подделает.

**21. Поддерживается ли HTTP/2?**
Сервер и клиент — да, автоматически по TLS (ALPN); h2c (без TLS) — отдельно. Мультиплексирование запросов в одном соединении.

**22. Когда сторонний роутер (chi/gin/echo/fiber)?**
Когда нужны группы, встроенные middleware, параметры, производительность хеш-таблиц маршрутов. Стандартный mux — сильный baseline с 1.22.

## Раздел 25. gRPC и Protobuf

**1. Что такое gRPC?**
RPC-фреймворк поверх HTTP/2 с protobuf-сериализацией: контракты в .proto, кодогенерация клиентов/серверов, стриминг, дедлайны, интерсепторы.

**2. Почему protobuf?**
Бинарный компактный формат со схемой: быстрее и меньше JSON, строгая типизация, обратная совместимость через номера полей.

**3. Какие типы вызовов есть?**
Unary (запрос-ответ), Server streaming (один запрос — поток ответов), Client streaming (поток запросов — один ответ), Bidirectional streaming (два независимых потока).

**4. Как описывается сервис?**
```proto
service UserService {
  rpc GetUser(GetUserRequest) returns (User);
}
```
`protoc` + `protoc-gen-go`/`protoc-gen-go-grpc` генерируют код.

**5. Что такое metadata?**
Ключ-значения в контексте (аналог заголовков): `metadata.FromIncomingContext(ctx)` на сервере, `metadata.AppendToOutgoingContext(ctx, ...)` на клиенте. Для trace-id, auth-токенов.

**6. Что такое интерсепторы?**
Middleware gRPC: `UnaryServerInterceptor` (и stream-версии) — логирование, recovery, auth, метрики, retry. Клиентские и серверные, цепочкой.

**7. Как работать с ошибками?**
`status.Errorf(codes.NotFound, "user %d", id)` на сервере; на клиенте — `status.FromError(err)` → код и сообщение. Коды: InvalidArgument, NotFound, PermissionDenied, Unavailable, Internal...

**8. Как передаются дедлайны?**
Клиент ставит таймаут в контекст — gRPC прокидывает его по цепочке вызовов; сервер видит отмену в ctx и обязан уважать (не делать тяжёлую работу после отмены).

**9. Правила совместимости .proto?**
Не менять номера полей и типы; удалять — только через `reserved`; новые поля — добавляются (старые клиенты их игнорят); enum — только добавлять значения; имена менять нельзя.

**10. Что такое `oneof`?**
Сумма-тип: ровно одно из нескольких полей. Генерирует удобный тип-дискриминатор — для полиморфных сообщений (например, разные типы событий).

**11. Как настраивается клиент?**
`grpc.NewClient(addr, creds...)` (новый API; `grpc.Dial` устарел): insecure-креды для dev, TLS для прод. По умолчанию подключение ленивое.

**12. Нюансы балансировки gRPC?**
Долгоживущие HTTP/2-соединения: L4-балансировка «прилипает» к одному поду. Решения: client-side LB (round robin + resolver), headless-сервисы, L7-прокси.

**13. Как устроен health check?**
Стандартный сервис `grpc.health.v1`: клиент опрашивает статус — совместимый механизм readiness для LB/k8s.

**14. Инструменты разработки?**
`buf` (линтер/брейкинг-чеки .proto), `grpcurl` (тест вызовов из CLI), server reflection (включать в dev), `protoc-gen-validate`/`protovalidate` для валидации сообщений.

## Раздел 26. Работа с БД

**1. Что такое `database/sql`?**
Стандартный интерфейс поверх драйверов (PostgreSQL — pgx/lib-pq, MySQL...). Драйвер регистрируется через blank-импорт `_ "github.com/jackc/pgx/v5/stdlib"`.

**2. Что такое `*sql.DB`?**
Не соединение, а пул соединений; потокобезопасен. Создаётся один на приложение (`sql.Open` — ленивый, подключение проверяют `Ping`).

**3. Ключевые настройки пула?**
`SetMaxOpenConns` (лимит нагрузки на БД), `SetMaxIdleConns` (кэш соединений), `SetConnMaxLifetime` (ротация — против обрывов и балансировки), `SetConnMaxIdleTime`.

**4. `Query` / `QueryRow` / `Exec` — когда что?**
`Query` — множество строк (Rows); `QueryRow` — одна строка (или `sql.ErrNoRows`); `Exec` — команды без результата (INSERT/UPDATE/DELETE), проверяют `RowsAffected`.

**5. Жизненный цикл `*sql.Rows`?**
`defer rows.Close()`; итерация `rows.Next()` → `rows.Scan(...)`; после цикла обязательно `rows.Err()` — ошибки итерации не «выпадут» иначе.

**6. Как читать NULL-значения?**
`sql.NullString/NullInt64/NullFloat64/NullTime` или указатели `*string` — nil соответствует NULL. Выбирать по вкусу команды, но единообразно.

**7. Нюансы `Scan`?**
Типы аргументов должны соответствовать колонкам; `[]byte` против `string`; время — `time.Time`; дженерик-вариант — `rows.Collect` в pgx.

**8. Зачем `Prepare`/`Stmt`?**
Прекомпиляция запроса: повторные вызовы дешевле, защита от инъекций; для батчей — обязательно. В pgx кэш prepared statements включён по умолчанию.

**9. Как работать с транзакциями?**
```go
tx, err := db.BeginTx(ctx, nil)
defer tx.Rollback() // no-op после Commit
...
tx.Commit()
```
Все операции внутри — через `tx.*`, не `db.*`.

**10. Как транзакции связаны с пулом?**
Транзакция занимает одно соединение до Commit/Rollback. Смешивать `db.*` и `tx.*` нельзя; много параллельных tx — риск исчерпания пула (дедлок на пуле).

**11. Как защищаться от SQL-инъекций?**
Только плейсхолдеры (`$1`, `?` — по драйверу); никаких `fmt.Sprintf` в SQL. Имена таблиц/колонок параметрами быть не могут — белый список.

**12. Как различать ошибки БД?**
`errors.Is(err, sql.ErrNoRows)`; PostgreSQL — `pgconn.PgError` с кодом (23505 — unique violation) через `errors.As`. Транслировать в доменные ошибки на уровне репозитория.

**13. Как делать миграции?**
golang-migrate, goose, atlas: файлы миграций в репо, авто-applay при деплое или отдельным шагом; идемпотентность и down-скрипты.

**14. ORM или голый SQL?**
GORM — быстрый старт, «магия», тяжело контролировать SQL; ent — схемы + кодогенерация; sqlc — SQL-first + типобезопасный кодоген; голый database/sql/pgx — максимум контроля. Выбор по сложности домена и команде.

**15. Что такое N+1 и как лечить?**
Запрос в цикле на каждую запись → 1+N обращений. Лечение: JOIN, батч-запрос `WHERE id = ANY($1)`, кэш справочников. Видно в логах трассировки и на профиле latency.

**16. Как задавать таймауты на запросы?**
Контекст в каждом вызове (`QueryContext`) + разумный дедлайн; соединения с `ConnMaxLifetime` — против «зависших» коннектов.

**17. Как быстро вставлять много строк?**
PostgreSQL: `COPY` (pgx) или multi-values INSERT / батч через prepared stmt. Построчный Exec на тысячи строк — на порядки медленнее.

**18. Как подключаться к Redis?**
`github.com/redis/go-redis/v9`: клиент с внутренним пулом, ctx в каждом вызове; pipelines для батчей; pub/sub, streams для событий.

**19. Что такое singleflight и при чём тут кэш?**
`golang.org/x/sync/singleflight`: дедупликация параллельных одинаковых запросов — один полетел в БД, остальные ждут результат. Лечит cache stampede при истечении горячих ключей.

**20. Как диагностировать медленные запросы?**
`EXPLAIN ANALYZE` на стороне БД, логи медленных запросов, метрики latency драйвера, block-профиль Go (ожидание пула). Частая причина в Go-коде — исчерпание `MaxOpenConns`.

## Раздел 27. Архитектура и паттерны проектирования

**1. Типовые слои Go-сервиса?**
Transport (http/grpc handlers) → Service/Usecase (бизнес-логика) → Repository (доступ к данным). Зависимости направлены внутрь: домен не знает о HTTP и SQL.

**2. Кто объявляет интерфейс в Go-архитектуре?**
Потребитель: пакет service объявляет `type Storage interface {...}`, реализация (postgres) подключается снаружи. Меньше связности, проще моки, интерфейс ровно под нужды сервиса.

**3. Что такое чистая архитектура в Go-исполнении?**
Доменные сущности и use-case'ы в центре; адаптеры (репозитории, HTTP) снаружи; правило зависимостей «внутрь». Практически — без тяжёлых DI-фреймворков: конструкторы и композиция в main.

**4. Как делается dependency injection?**
Явно: `NewService(repo Repo, logger *slog.Logger, cfg Config)`. Вся сборка графа — в main/композиционном корне. Для огромных проектов — google/wire (кодогенерация).

**5. Паттерн Repository — что скрывает?**
Детали хранилища за интерфейсом доменных операций: `FindUser(ctx, id) (User, error)`, доменные ошибки вместо SQL. Смена БД/драйвера не затрагивает сервис.

**6. Что такое functional options?**
```go
type Option func(*Server)
func WithTimeout(d time.Duration) Option { return func(s *Server) { s.timeout = d } }
NewServer(addr, WithTimeout(3*time.Second))
```
Расширяемые конструкторы без ломающих изменений сигнатур.

**7. Как в Go делают синглтон?**
`sync.Once` + пакетная переменная. Идеологически предпочитают явную зависимость: глобальное состояние мешает тестам и распараллеливанию.

**8. Что такое adapter/anti-corruption layer?**
Обёртка над внешним API, переводящая его модели в доменные: внешний контракт не протекает в домен, смена вендора локализована.

**9. Anemic vs rich domain — в чём практическая разница?**
Anemic: структуры-контейнеры + вся логика в сервисах. Rich: методы на доменных типах (вместе с инвариантами). В Go обычно гибрид: инварианты на типах, оркестрация в сервисах.

**10. Где ставить транзакционные границы?**
В use-case/сервисе: он открывает транзакцию и передаёт исполнителя в репозитории (TxManager/интерфейс `WithinTx(ctx, fn)`) либо собирает батч операций репозитория.

**11. Каноничный layout проекта?**
`cmd/app/main.go`, `internal/` (domain, service, repo, transport), `api/` (контракты), `migrations/`, `configs/`. Внутренние детали — только под `internal/`.

**12. Что даёт пакет `internal`?**
Импорт разрешён только внутри родительского дерева модулей: внешние проекты не могут тянуть ваши внутренние пакеты — защита API.

**13. Как бороться с циклическими импортами?**
Выделить общие типы в отдельный пакет; интерфейсы объявлять у потребителя; развязать событиями/коллбэками. Циклы — всегда сигнал о границах пакетов.

**14. Что такое outbox-паттерн?**
Событие пишется в таблицу outbox в той же транзакции, что и данные; отдельный процесс доставляет его в брокер. Решает «записали в БД, но событие потеряли».

**15. Как управлять конфигурацией?**
env-переменные (12-factor) + файл для локали; структурированный `Config` с валидацией на старте (fail fast). Секреты — из секрет-стора, не в коде.

**16. Как логировать идиоматично?**
`slog` (Go 1.21): структурные записи, уровни, атрибуты; request-id/correlation-id через контекст; не логировать секреты и PII; лог на границе ошибки, а не в каждом слое.

**17. Какие метрики собирать?**
Prometheus: counters (запросы/ошибки), histograms (latency), gauges (очереди, соединения). Модель RED для API: Rate, Errors, Duration.

**18. Как устроен трейсинг?**
OpenTelemetry: span на входе запроса, дети — на внешние вызовы/БД; propagation через контекст. Смотреть p99 по спанам, зависимые задержки.

**19. Как эволюционировать API?**
Версионирование префиксом (`/v1/`), обратно совместимые изменения, feature flags, контрактные тесты. Для gRPC — правила совместимости proto.

**20. Что делает код поддерживаемым на практике?**
Маленькие интерфейсы у потребителей, явные зависимости, тесты на границах слоёв, единый стиль (lint), домен без транспорта/БД, именование без аббревиатур-загадок.

## Раздел 28. Инструменты, модули и сборка

**1. Базовые команды go mod?**
`go mod init`, `go mod tidy` (добавить/убрать зависимости), `go mod download/verify`. `go.sum` — хеши версий, коммитится.

**2. Что такое минимальный выбор версий (MVS)?**
Алгоритм go modules: выбирается минимальная версия, удовлетворяющая всем требованиям графа — детерминированно, без «последней всегда».

**3. Как работает версионирование v2+?**
Мажорная версия — часть пути импорта (`github.com/x/pkg/v2`) — semantic import versioning. Позволяет сосуществовать мажорам.

**4. Зачем `replace` и `vendor`?**
`replace` — локальная версия/форк зависимости (отладка, патч). `vendor/` — зависимости в репо: воспроизводимость сборки, скорость CI, аудит.

**5. Что такое `go.work`?**
Workspace для мульти-модульного репо: локальные связи модулей без правки go.mod, удобная разработка нескольких сервисов сразу.

**6. Повседневные команды Go?**
`go build`, `go run`, `go test ./...`, `go fmt`/`gofmt`, `go vet`, `go doc`, `go generate ./...`, `go install`.

**7. Как собрать кросс-платформенно?**
`GOOS=linux GOARCH=arm64 go build`; `CGO_ENABLED=0` — чисто статический бинарник без libc.

**8. Каноничный Dockerfile для Go?**
Мультистейдж: builder (`golang:alpine`) → runtime (`scratch`/`distroless`/`alpine`): только бинарник, non-root user, HEALTHCHECK. Образ — десятки МБ.

**9. Что делают ldflags при сборке?**
`-X main.version=$VERSION` — инъекция версии в переменную; `-s -w` — убрать таблицы символов (меньше бинарник). Приложения должны показывать версию по флагу.

**10. Чем проверять код статически?**
`go vet` (встроенный, в тестах и CI), `staticcheck` (набор проверок), `golangci-lint` — агрегатор (errcheck, revive, gosec, dupl...). Настройка под команду, а не «всё включено».

**11. gofmt vs goimports?**
gofmt — каноничное форматирование; goimports — плюс управление импортами. В CI — проверка «после форматирования нет diff».

**12. Чем отлаживать?**
Delve: `dlv debug`, брейкпоинты, просмотр горутин, шаги. Интеграция в IDE; `print`-дебаг — только как быстрый способ.

**13. Как профилировать запущенный бинарник?**
Символы берутся из бинарника: `go tool pprof binary profile.out` — красивые стектрейсы даже с символами prod-сборки.

**14. Минимальный CI для Go-проекта?**
lint (golangci-lint) → vet → `go test -race -cover` → build → security-scan (govulncheck) → сборка образа. Кэш модулей для скорости.

**15. Что делает govulncheck?**
Проверяет зависимости на известные CVE с учётом реально используемых функций — меньше ложных срабатываний, чем «слепой» скан.

**16. Для чего `go:generate`?**
Кодогенерация: mockery, stringer, protoc, sqlc. `go generate ./...` в CI гарантирует, что сгенерированный код актуален.

**17. Как работать с приватными модулями?**
`GOPRIVATE=corp.example/*` — обход публичного прокси/sumdb; SSH-токен/credential helper для git. Точки подключения настраиваются в env CI.

**18. Что даёт goreleaser?**
Автоматизация релизов: сборка под все платформы, архивы, docker-образы, changelog, публикация на GitHub Releases — одной командой из тега.

## Раздел 29. Разбор каверзных сниппетов

**1. Что выведет код (замыкание на переменную цикла)?**
```go
funcs := []func(){}
for _, v := range []int{1, 2, 3} {
    funcs = append(funcs, func() { fmt.Println(v) })
}
for _, f := range funcs { f() }
```
До Go 1.22 — `3 3 3`: переменная `v` одна, все замыкания видят финальное значение. С Go 1.22 — `1 2 3` (пересоздание на итерации). Вопрос до сих пор спрашивают — чтобы проверить понимание замыканий.

**2. Что выведет defer в цикле?**
```go
for i := 0; i < 3; i++ { defer fmt.Println(i) }
```
`2 1 0`: аргументы фиксируются при регистрации, порядок LIFO.

**3. Что произойдёт с `a`?**
```go
a := []int{1, 2, 3, 4}
b := a[:2]
b = append(b, 99)
fmt.Println(a)
```
`[1 2 99 4]` — append влез в cap и записал в общий массив.

**4. Что будет при записи в nil map?**
```go
var m map[string]int
m["a"] = 1
```
Паника `assignment to entry in nil map`. Чтение — безопасно.

**5. Что выведут два одинаковых цикла по map?**
Порядок разный: рандомизация стартовой точки — специально. Детерминизм — через сортировку ключей.

**6. Что вернёт эта функция и почему?**
```go
func f() error { var e *MyErr; return e }
fmt.Println(f() == nil) // false
```
В интерфейсе лежит (тип *MyErr, значение nil) — интерфейс не равен nil. Возвращать `nil` явно.

**7. Что вернёт чтение из закрытого канала?**
```go
ch := make(chan int, 1); close(ch)
v, ok := <-ch // v = 0, ok = false
```
Немедленно, нулевое значение + ok=false.

**8. Что будет при `close(ch); ch <- 1`?**
Паника `send on closed channel`.

**9. Насколько детерминирован вывод select с двумя готовыми каналами?**
Никак: псевдослучайный равновероятный выбор — защита от голодания.

**10. Что изменится в `s`?**
```go
s := []int{1, 2, 3} // cap 3
t := s[:1]
t = append(t, 100)
fmt.Println(s)
```
`[1 100 3]` — реслайс + append перезаписал элемент исходного среза.

**11. Что выведет код с range по срезу структур?**
```go
type P struct{ N int }
ps := []P{{1}, {2}}
for _, p := range ps { p.N = 99 }
fmt.Println(ps)
```
Без изменений `[1 2]`: `p` — копия. Менять нужно `ps[i].N`.

**12. Что выведет iota-блок?**
```go
const ( a = iota; b; c )
```
`0 1 2`; после `a = iota` остальные наследуют выражение. Пропуск — `_`, сдвиг — `1 << iota`.

**13. Гарантированно ли напечатается строка?**
```go
go fmt.Println("hi")
```
Нет: main может завершиться раньше. Нужна синхронизация (WaitGroup/канал).

**14. Что вернёт функция с defer и named return?**
```go
func f() (x int) { defer func(){ x++ }(); return 1 }
```
`2`: return присваивает 1, defer меняет x, затем выход.

**15. Что выведет `fmt.Println(5/2, 5.0/2, string(65))`?**
`2 2.5 A`: целочисленное деление; float; `string(65)` — руна `'A'`, а не «65» (для числа в строку — `strconv.Itoa`).

**16. Что напечатает код с затенением err?**
```go
err := errors.New("outer")
if true { err := errors.New("inner"); _ = err }
fmt.Println(err)
```
`outer`: внутренний `err :=` затенил внешний — ошибка из блока не уйдёт наружу.

**17. Чем плох `time.After` в горячем цикле select?**
Аллоцирует новый таймер на каждой итерации; таймеры живут до срабатывания. Для циклов — `time.NewTimer` + `Reset`.

**18. Что не так с `len("aф")` и `s[1]`?**
`len` — байты (3), индексация — байты: `s[1]` даст половину кириллической руны. Символы — через `[]rune`/range.

## Раздел 30. Системный дизайн и практические вопросы

**1. Спроектируйте rate limiter.**
Локально — token bucket (`golang.org/x/time/rate`). Распределённо — Redis: счётчик `INCR` + `EXPIRE` или sliding window на Lua (атомарно). Различать лимиты: per-user, per-endpoint, глобальный. Ответ при превышении — 429 + Retry-After.

**2. Кэш в памяти с TTL — как построить?**
Map + RWMutex; в значении — expiry; фоновая чистка (janitor) или чистка при чтении; singleflight против stampede при истечении горячих ключей. Готовое — ristretto/otter (с eviction). Обязателен лимит размера.

**3. Как обеспечить идемпотентность обработки?**
Ключ идемпотентности от клиента → таблица обработанных (уникальный индекс) → повтор игнорируется/возвращается прошлый результат. Обработка и запись ключа — атомарно (одна транзакция).

**4. Как правильно ретраить?**
Экспоненциальный backoff + jitter, ограничение попыток, retry только идемпотентных операций и retryable-ошибок (таймауты, 5xx, Unavailable), уважение контекста и Retry-After. Circuit breaker — против шторма ретраев.

**5. Что такое circuit breaker?**
Состояния: closed (нормально) → open (сбойная серия — запросы отваливаются сразу) → half-open (пробные). Библиотека sony/gobreaker. Защищает от каскадных отказов и перегрева зависимой системы.

**6. Что такое backpressure и как её устроить?**
Не принимать больше, чем можем обработать: ограниченные очереди, семафоры, 429/отказ на входе, ограниченный параллелизм потребителей. Бесконечная очередь — просто отложенный OOM.

**7. Порядок graceful shutdown сервиса?**
Сигнал → снять с балансировки/readiness=false → перестать принимать новые запросы → drain текущих (таймаут) → завершить фоновые воркеры → закрыть БД/брокер → exit. Каждый шаг — со своим таймаутом.

**8. Liveness против readiness?**
Liveness — процесс жив (без проверки зависимостей, иначе каскад перезапусков). Readiness — готов принимать трафик (БД/кэш достижимы, воркеры не переполнены). Startup probe — для тяжёлой инициализации.

**9. Как обработать 1 млн сообщений в минуту?**
Оценить: среднюю/пиковую стоимость обработки. Решения: батчинг, партиционирование по ключу (порядок в партиции), фиксированные воркеры по партициям, идемпотентность, мониторинг lag, горизонтальное масштабирование групп потребителей.

**10. Как принимать большие файлы?**
Стриминг: multipart → прямо в объектное хранилище (или на диск) без ReadAll; presigned URL — клиент грузит напрямую; лимиты размера, антивирус асинхронно.

**11. Как сделать распределённый лок?**
Redis `SET NX PX` + токен владельца (fencing при записи) / redsync; TTL обязателен (иначе мёртвый лок держит всё); для строгой корректности — БД-лок/консенсус. Помнить: лок — для оптимизации, не для абсолютной гарантии.

**12. Как снижать latency API?**
Профиль → hot path: убрать N+1, батчировать запросы, кэш (по TTL/invalidation), параллельные независимые вызовы (errgroup), предвычисления, keep-alive, ближе к данным (регионы). Измерять p99, не среднее.

**13. Какие метрики смотреть у сервиса?**
RED (Rate, Errors, Duration) на API; USE (Utilization, Saturation, Errors) на ресурсы; saturation-признаки: длина очередей, лаги, пулы (БД-коннекты), goroutines; business-метрики. Алерты на симптомы (латентность/ошибки), не на CPU.

**14. Как выпускать релизы без даунтайма?**
Rolling (k8s) с graceful drain; blue-green для мгновенного отката; canary — постепенный трафик с метриками. Миграции — expand-migrate-contract: сначала обратно совместимая схема, потом код, потом чистка.
